# CLI スキャン API セキュリティ

このページでは、セキュリティレビュアーや運用担当者向けに、OsWL が**自動スキャン送信**（`POST /api/scan`）をどのように保護しているかを説明します。日常的なセットアップについては[CLI 連携](CLI-Integration.md)を参照してください。このページはそれに代わるものではありません。

---

## ブラウザと CLI が異なる理由

| クライアント | 認証 | CSRF（ブラウザトークン） |
|--------|----------------|----------------------|
| **Web UI** | セッションクッキー＋ログイン | 状態を変更するリクエストで必須 |
| **CLI / CI** | `Authorization: Bearer` プロジェクト API キー＋提出者の資格情報 | 未使用 — セッションクッキーなし |

クロスサイトリクエストフォージェリ対策は**クッキーベースのブラウザセッション**に適用されます。CLI はヘッダーと本文に明示的なシークレットを送信するため、ログイン中のブラウザセッションに依存しません。

そのため OsWL は次のパス**のみ**を CSRF チェックから除外します:

- `POST /api/scan` — スキャンペイロードの送信
- `POST /api/scan/parse` — マニフェストアーカイブの解析（CLI ステップ 1）
- `POST /api/scan/gate` — CI からの PR ゲート評価（API キー認証、ブラウザセッションなし）
- `GET /api/scan/ping` — API キーの確認

それ以外のすべてのルートは、UI 向けの通常の CSRF 保護を維持します。

---

## 認証モデル（3 段階のチェック）

| ステップ | 検証内容 |
|------|------------------|
| 1 | `Authorization: Bearer …` の**プロジェクト API キー** |
| 2 | JSON 本文内の**提出者**のメールアドレスとパスワード |
| 3 | 提出者が **`SCAN_SUBMIT`**（ロールテンプレートの権限）を持ち、そのプロジェクトの **`project_members`** に登録されていること |

ロールテンプレートとプロジェクトメンバーシップの違いについては[権限レイヤー](Authorization-Layers.md)を参照してください。

---

## 悪用への耐性

- API キーまたはパスワードの失敗した試行は**レート制限**されます（設定可能）。
- 失敗は**監査ログ**に記録されます（`SCAN.API_KEY_FAILURE`、`SCAN.AUTH_FAILURE`、`SCAN.AUTH_RATE_LIMITED`）。
- 成功した取り込みは、監査ログ内で**提出者のメールアドレス**（`actorEmail` / detail）とともに `SCAN.INGEST` として記録されます。OsWL は `scan_results` に `submitted_by_user_id` カラムを保存しません。
- CLI キーの発行は、**現在のセッションユーザー**を行為者として `CLI_KEY.CREATE` に記録されます（`api_keys` のカラムではありません）。

---

## スキャン状態のポーリング（ブラウザ）

`GET /api/scan/{scanId}/status` は API キーのみの経路ではなく、**Web セッション**と**プロジェクトメンバーシップ**を使用します。通常のログインおよび CSRF ルールの対象のままです。

レスポンスはスキャン状態と **AI エンリッチメント（`aiStatus`）を別々に**追跡します。AI サマリーがバックグラウンドでまだ `PENDING`/`RUNNING` の間にも、スキャンは `COMPLETED` に到達し得ます。スキャンの完了を AI インサイトの準備完了とみなさず、`aiStatus` をポーリングしてください。

---

## 運用上の推奨事項

- エンドツーエンドで **HTTPS** を使用する（本番ではリバースプロキシ経由）。
- プロジェクト API キーと提出者のパスワードは本番用のシークレットとして扱い、漏洩時はローテーションする。
- インシデント発生後は、スキャン認証失敗に関する監査ログフィルターを見直す。
- `SCAN_SUBMIT` とプロジェクトメンバーシップを持つ CI 専用のサービスアカウントを使用することを推奨する。

提出者のパスワードは現在 JSON 本文で送信されます — TLS を使用し、監査イベントを監視してください。将来のリリースではトークンベースの CLI 認証が追加される可能性があります — リリースノートを確認してください。
