# 権限レイヤー (Authorization layers)

**対象読者:** 開発者、セキュリティレビュアー、ライセンス・コンプライアンス担当者、IT 運用、経営層 — ソースコードを読まずに OsWL で*誰が何をできるか*を理解したいすべての人。

---

## 一言でいうと

OsWL は **3 つの独立した概念**を組み合わせています。日常の言葉では似たような表現が使われます（「管理者」「ロール」「メンバー」）が、製品の中では意味が異なります:

| 概念 | わかりやすい名前 | 答える質問 |
|------|---------------------|-----------------|
| **A** | **ロールテンプレート**（インスタンス全体） | 「この人はスキャン送信、ライセンスのエクスポート、設定などの機能を使えるか?」 |
| **B** | **プロジェクトメンバーシップ** | 「この人は**このプロジェクト**のデータを開けるか?」 |
| **C** | **システム管理者** | 「この人は OsWL インスタンス全体（ユーザー、監査ログ、すべてのプロジェクト）を管理できるか?」 |

通常のユーザーがプロジェクトで作業するには、通常 **A と B の両方**が必要です:

- **A** — 例: ライセンスページを開くための `LICENSE_VIEW`
- **B** — そのプロジェクトの `project_members` に登録されていること

**システム管理者（C）** は、サポートとガバナンスのため、メンバーシップに関係なくすべてのプロジェクトにアクセスできます。

> **開発者向けの命名のヒント:** コードやドキュメントでは「ロール」単独ではなく**ロールテンプレート**と呼んでください。「プロジェクト管理者」ではなく**プロジェクトメンバーシップ**と呼んでください（プロジェクトレベルの `ADMIN` メンバーシップタイプを指す場合を除く）。

---

## レイヤー A — ロールテンプレート（Admin / Developer / Viewer）

- **設定 → 管理者 → ロールテンプレート**で構成します。
- ユーザーが招待または編集される際に割り当てられます。
- **権限**の集合として実装されます（例: `SCAN_SUBMIT`、`SECURITY_CENTER_VIEW`）。

### 内蔵テンプレート（空のデータベースの初回起動時）

初回起動時、OsWL は後から調整可能な 3 つのテンプレートを作成します:

| テンプレート | 主な用途 | 概要 |
|----------|-------------|---------|
| **Admin** | インスタンスの所有者／プラットフォーム管理者 | カタログ内のすべての権限 |
| **Developer** | スキャン・トリアージを行うエンジニア | プロジェクト・スキャン・セキュリティセンター（状態更新とエクスポートを含む）、ライセンス閲覧／エクスポート、VCS・CLI キー |
| **Viewer** | 読み取り専用の関係者 | プロジェクト・スキャン・セキュリティセンター・ライセンスページとエクスポートの閲覧 — スキャン送信・設定は不可 |

これらの名前は **OsWL インスタンス全体にわたる機能**を表します。「プロジェクト #42 のメンバー」であることとは**同じではありません**。

---

## レイヤー B — プロジェクトメンバーシップ

- **`project_members`** テーブルに保存されます（ユーザー × プロジェクトごとに 1 行）。
- 「このユーザーは**プロジェクト ID X** のデータを見たり変更したりできるか?」に答えます。
- プロジェクト単位の画面や API（セキュリティセンター、スキャン履歴、ライセンスエクスポート、API キーなど）で **`ProjectAccessService`** により適用されます。

### プロジェクトメンバーのロール（技術的詳細）

各メンバーシップ行にはプロジェクト単位のロールがあります:

| 値 | 現在の意味 |
|-------|-------------|
| **ADMIN** | プロジェクト作成時に作成者へ割り当てられる |
| **MEMBER** | 追加された他のメンバーの既定値 |

現時点では、**機能へのアクセスは引き続きレイヤー A（権限）に従います**。プロジェクトメンバーシップは主に**プロジェクト間の不正アクセス（IDOR）**を防ぐ役割を果たします。今後、ADMIN/MEMBER フィールドを使って「プロジェクトオーナー vs ゲスト」をより細分化するルールが追加される可能性があります。

### メンバーシップが自動的に付与されるケース

- プロジェクトを**作成した**ユーザーは、プロジェクトの **ADMIN** として追加されます。
- 起動時に、メンバーがまだいなかった既存プロジェクトへ作成者を追加する一度限りのブートストラップが実行されます。

**コラボレーションに関する注記:** 既存のプロジェクトへ 2 人目のユーザーにアクセスさせるには、そのユーザーが `project_members` に含まれている必要があります（現在は作成者について自動的に行われます。より広いチーム割り当てには運用プロセスや将来の UI が必要になる場合があります）。

---

## レイヤー C — システム管理者

- ユーザーアカウントのフラグ（`isSystemAdmin`）で、**セットアップウィザード**経由で作成されます。
- **設定 → 管理者**（ユーザー、ロールテンプレート、監査ログ）を開けます。
- **プロジェクトメンバーシップを迂回**します — サポートのためどのプロジェクト ID でも開けます。
- ログイン、2FA、セッションセキュリティは他のユーザーと同じものを使用します。

次と混同しないでください:

- **「Admin」という名前のロールテンプレート** → 権限バンドルにすぎない
- **プロジェクトメンバーシップの ADMIN** → 1 つのプロジェクトの作成者にすぎない

## 各レイヤーの連携（例）

| 人物 | ロールテンプレート | プロジェクト #5 のメンバー? | プロジェクト #5 のセキュリティセンターを開けるか? |
|--------|---------------|-------------------|--------------------------------------|
| システム管理者 | 任意 | 任意 | 可能（C がメンバーシップを迂回） |
| Developer | Developer | はい、#5 のメンバー | 可能（A + B） |
| Developer | Developer | いいえ、#5 にいない | 不可 — スキャン権限があっても B に阻まれる |
| Viewer | Viewer | はい、#5 のメンバー | 可能、Viewer テンプレートの範囲の読み取り専用機能 |
| Viewer | Viewer | はい、ただし `SCAN_SUBMIT` なし | CLI スキャンの送信は不可（A）、B を満たしていれば閲覧は可能 |

## CLI スキャン（追加のチェック）

`POST /api/scan` はブラウザではなく自動化のために設計されています。次を要求します:

1. 有効な**プロジェクト API キー**
2. **`SCAN_SUBMIT`**（レイヤー A）を持つ提出者の**メールアドレス＋パスワード**
3. 提出者がそのプロジェクトの**`project_members`**に登録されていること（レイヤー B）

失敗した試行は**監査ログ**に記録されます。[CLI 連携](CLI-Integration.md)と[スキャン API セキュリティ](Scan-Api-Security.md)（概要のみ）を参照してください。

## 本番運用とガバナンス

- OsWL は**多層防御**を前提に構築されています: セッションログイン、任意の 2FA、権限チェック、プロジェクトメンバーシップ、API キー、レート制限、監査ログ、強化された本番既定値。
- 運用の詳細（環境変数、リバースプロキシ、ヘルスチェック）は[運用デプロイチェックリスト](Production-Deployment-Checklist.md)を参照してください。
- 技術的な適用ポイントとエンドポイント一覧: [プロジェクトアクセス制御](Project-Access-Control.md)。
