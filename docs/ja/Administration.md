# 管理

[1.0.5.1 の変更点](Whats-New-v1.0.5.1.md)

このページでは管理者専用の機能をすべて扱います: ユーザー管理、ロールテンプレート、監査ログ、セキュリティ設定、SMTP 設定。

> 特に断りのない限り、このページのすべての操作には**システム管理者**権限が必要です。

ここでのロールテンプレートは**インスタンス全体の権限**を制御するものであり、ユーザーがどのプロジェクトを開けるかを制御するものではありません。[権限レイヤー](Authorization-Layers.md)を参照してください。

## スキャン判定の保存

新しいデータ解析は完了状態を公開する前にバージョン付き判定を保存します（V43スキーマ）。ライブラリ識別情報、ライセンス根拠・分類、プロバイダー照会状態・時刻、OSV修正バージョン評価と個別の脆弱性を記録し、修正バージョン競合、スコア・KEV情報の欠落、出典も保持します。レポートとスキャン集計は共有Library/CVEが更新されても保存した判定を使います。再キャプチャや古いスキャンオブジェクトの保存でも最初の判定は置換しません。不正な保存形式は空の結果に置き換えず失敗します。

判定のない既存スキャンは従来のライブ・アーカイブ参照を継続し、過去の判定を再構成しません。確認・猶予状態とレポート生成時刻は現在の値です。Security Center詳細などLibrary/CVEの直接参照は移行が必要で、完全な不変評価履歴ではありません。独立したAI出力はデータ解析判定に含みません。プロバイダー結果の同時保存や部分解析失敗の既存の限界も残り、この保存だけで全プロバイダーの照会成功を証明しません。元のオフライン世代参照はスキャンに残します。保存期間と別の再評価revisionは残作業です。


CIゲートも対象・基準スキャンの保存済み脆弱性・ライセンス・悪性パッケージ判定を使います。保存時の照会失敗、悪性判定根拠の欠落、構成一覧の不一致を最新の共有データで補って通過させません。確認・ソース解析結果・ポリシー選択は現在の状態で、保存判定のない既存スキャンはライブデータを使います.

## ユーザー管理

**設定 → 管理者 → ユーザー**

### ユーザーの招待

1. **ユーザーを招待**をクリックします。
2. ユーザーの**メールアドレス**と**表示名**を入力します。
3. 1 つ以上の**ロールテンプレート**を割り当てます。
4. **招待を送信**をクリックします（メールが無効な場合は**作成** — 仮パスワードが生成されます）。

ユーザーは仮パスワードが記載されたメールを受け取り、初回ログイン時に変更を強制されます。

### ユーザーの編集

| 操作 | エンドポイント |
|---|---|
| 表示名の変更 | `PUT /api/admin/users/{id}/display-name` |
| ロールの更新 | `PUT /api/admin/users/{id}/roles` |
| アカウントの有効化 | `PUT /api/admin/users/{id}/activate` |
| アカウントの無効化 | `PUT /api/admin/users/{id}/deactivate` |
| ユーザーの削除 | `DELETE /api/admin/users/{id}` |

> 無効化されたユーザーはログインできませんが、そのデータ（監査ログ、スキャンの帰属情報）は保持されます。

### セルフサービスによるアカウント削除

**システム管理者**を除く認証済みユーザーは誰でも、現在のパスワードを確認したうえで、ユーザーメニューから自分自身のアカウントを削除できます（**アカウントを削除**）。

| 項目 | 動作 |
|---|---|
| エンドポイント | `POST /api/my/delete-account` — ユーザー ID はセッションのプリンシパルからのみ取得されます（パス／ボディのユーザー ID は使用しません） |
| システム管理者 | 自己削除不可 |
| 削除対象 | `users` 行、`project_members` 行、保存済み VCS トークン |
| 保持対象 | それまでのすべての**監査ログ**行（行為者のメールアドレス／名前／ID のスナップショット）、プロジェクト、スキャン、インポート履歴 |
| 監査アクション | `USER.SELF_DELETE` — ユーザー行が削除される**前**に記録されるため、`actor_user_id` と表示名がキャプチャされます |

管理者による削除は引き続き `DELETE /api/admin/users/{id}` 経由の `USER.DELETE` です。

## ロールテンプレート

**設定 → 管理者 → ロールテンプレート**

ロールテンプレートは、複数のユーザーに割り当てられる名前付きの権限セットです。

### 内蔵ロールテンプレート

**空のデータベースでの初回起動時**に、OsWL は編集可能な 3 つのテンプレートを作成します:

| テンプレート | 対象ユーザー |
|----------|-------------------|
| **Admin** | 権限カタログ全体（インスタンス運用者向け） |
| **Developer** | スキャン、トリアージ、ライセンス閲覧／エクスポート、VCS・CLI キー |
| **Viewer** | 読み取り専用の分析ページとエクスポート |

これらは**ロールテンプレート**（レイヤー A）です。すべてのプロジェクトにユーザーを自動的に追加するわけではありません — [権限レイヤー](Authorization-Layers.md)を参照してください。

追加のテンプレートを作成したり、権限をいつでも変更したりできます。

### 権限リファレンス

| 権限 | 説明 |
|---|---|
| `PROJECT_VIEW` | プロジェクト一覧・詳細の閲覧 |
| `PROJECT_CREATE` | 新規プロジェクトの登録（Quick Import または CLI） |
| `PROJECT_DELETE` | プロジェクトをゴミ箱へ移動 |
| `PROJECT_RESTORE` | ゴミ箱からプロジェクトを復元 |
| `PROJECT_PERMANENT_DELETE` | ゴミ箱からプロジェクトを完全削除 |
| `SCAN_SUBMIT` | CLI 経由でのスキャン送信（`POST /api/scan`） |
| `SCAN_VIEW` | スキャン結果の閲覧 |
| `SCAN_HISTORY_VIEW` | スキャン履歴一覧の閲覧 |
| `SECURITY_CENTER_VIEW` | セキュリティセンターの CVE 一覧の閲覧 |
| `SECURITY_CENTER_UPDATE_STATUS` | CVE トリアージ状態の更新 |
| `SECURITY_CENTER_EXPORT` | セキュリティセンター結果のエクスポート |
| `LICENSE_VIEW` | ライセンス分析ページの閲覧 |
| `LICENSE_EXPORT` | NOTICE ファイルおよび SPDX SBOM のダウンロード |
| `LICENSE_POLICY_MANAGE` | ライセンスポリシー項目の追加／編集／削除 |
| `SCAN_HISTORY_DELETE` | スキャン履歴からの項目削除 |
| `COMPONENT_DETAIL_VIEW` | コンポーネント詳細パネルの閲覧 |
| `VERSION_DIFF_VIEW` | バージョン比較の閲覧 |
| `RISK_TREND_VIEW` | リスクトレンドグラフの閲覧 |
| `SETTINGS_AI_MANAGE` | AI プロバイダー設定の構成 |
| `SETTINGS_VCS_MANAGE` | VCS 接続の追加／削除 |
| `SETTINGS_CLI_KEY_MANAGE` | プロジェクト CLI API キーの管理 |
| `SETTINGS_CACHE_MANAGE` | キャッシュ設定の管理 |
| `SETTINGS_SECURITY_MANAGE` | SMTP・2FA 設定の構成 |
| `ORG_DASHBOARD_VIEW` | **v1.0.4** — 組織ダッシュボード（`/org-dashboard`）の閲覧 |
| `AUDIT_LOG_VIEW` | **v1.0.4** — 監査ログの閲覧 |
| `AUDIT_LOG_EXPORT` | **v1.0.4** — SIEM 取り込み用の監査ログエクスポート |
| `SETTINGS_JIRA_MANAGE` | **v1.0.4** — Jira 連携の管理 |
| `SETTINGS_SNAPSHOT_MANAGE` | **v1.0.4** — オフラインスナップショットバンドルの管理 |

> v1.0.4 で追加された 5 つの権限は既存のロールテンプレートには**追加されず**、未付与の状態から始まります。特に `AUDIT_LOG_EXPORT` は監査記録をプラットフォーム外に送信するため、意図的に付与してください。

### テンプレートの作成

1. **新しいロールテンプレート**をクリックします。
2. 名前を入力します（例: "Developer"、"Security Analyst"、"Read Only"）。
3. 必要な権限にチェックを入れます。
4. **保存**をクリックします。

## セキュリティ設定（SMTP と 2FA）

**設定 → セキュリティ**

### SMTP（メールサーバー）

OsWL は二要素認証やユーザー招待の OTP メール送信に SMTP を使用します。

| 項目 | 説明 |
|---|---|
| **メールモード** | `DISABLED`（メールなし）、`SMTP`（標準リレー）、`STARTTLS` / `SSL_TLS` |
| **ホスト** | SMTP サーバーのホスト名 |
| **ポート** | SMTP ポート（通常 25、465、または 587） |
| **ユーザー名／パスワード** | SMTP 認証情報（パスワードは保存時に暗号化） |
| **送信者名／アドレス** | "From" に表示される名前とアドレス |

保存前に**テストメールを送信**をクリックして設定を確認できます。

### 二要素認証（2FA）

| モード | 動作 |
|---|---|
| `DISABLED` | OTP ステップなし — ユーザーはメールアドレス＋パスワードのみでログイン |
| `OPTIONAL` | OTP は利用可能だがユーザーはスキップできる |
| `REQUIRED` | すべてのユーザーがログインのたびに OTP ステップを完了する必要がある |

#### 信頼済みデバイス

2FA が有効な場合、ユーザーは OTP 認証に成功した後、ブラウザを**信頼済み**としてマークできます。信頼済みデバイスは、設定可能な期間（既定: 30 日間）OTP ステップをスキップします。

### パスワードポリシー

| 設定 | 既定値 | 説明 |
|---|---|---|
| 最小パスワード長 | `8` | 招待作成時とパスワード変更時に適用 |

## サーバープロパティ（application.yaml）

`application.yaml` または環境変数（Spring の relaxed binding）で設定するインスタンスレベルのセキュリティフラグです。設定 UI からは編集できず、再起動が必要です。

| 設定キー | 環境変数 | 既定値 | 説明 |
|---|---|---|---|
| `oswl.quick-import.allow-build-exec` | `OSWL_QUICK_IMPORT_ALLOW_BUILD_EXEC` | `false` | `false` の場合、Quick Import はマニフェストを**静的に**解析し、クローンしたリポジトリ内で見つかったビルドツール（`mvnw`、`gradlew`、`dotnet`）を決して実行しません。すべてのインポート対象リポジトリが信頼できる場合にのみ `true` に設定してください — ビルドベースのバージョン解決は OsWL ホスト上でリポジトリのビルドスクリプトを実行します。 |
| `oswl.security.trusted-proxies` | `OSWL_SECURITY_TRUSTED_PROXIES` | *(空)* | 信頼できるリバースプロキシの IP をカンマ区切りで指定します。直接の接続元がこの一覧に含まれる場合にのみ、`X-Forwarded-For` ヘッダーがクライアント IP の解決（監査ログ、レート制限）に使われます。空の場合、このヘッダーは無視されます。OsWL が自分の管理下にあるプロキシの背後で動作している場合のみ設定してください。 |
| `oswl.timezone` | `OSWL_TIMEZONE` | `Asia/Seoul` | 時刻依存の機能（現時点では AI 使用量の追跡 — 呼び出しがどの「日」に計上されるか）に使われるタイムゾーンです。デプロイの営業日が既定と異なるタイムゾーンに従うべき場合にのみ変更してください。 |

## 監査ログ

**設定 → 管理者 → 監査ログ**

監査ログはすべての重要なユーザーおよびシステムの操作を記録します。

| カラム | 説明 |
|---|---|
| **タイムスタンプ** | イベントが発生した時刻 |
| **行為者** | ユーザーのメールアドレスまたは `SYSTEM` |
| **アクション** | イベントコード（例: `SCAN.INGEST`、`AUTH.LOGIN_SUCCESS`、`LICENSE.EXPORT`） |
| **リソースタイプ** | 影響を受けたエンティティ（PROJECT、SCAN、USER など） |
| **リソース ID** | 影響を受けたエンティティの ID |
| **詳細** | 追加のコンテキスト（新しい値、バージョン文字列など） |

### フィルタリング

行為者、アクション（UI 上でグループ化 — 認証、ユーザー、プロジェクト、スキャン、CLI キー、コンポーネント、設定を含む）、日付範囲でフィルタリングできます。

**ユーザーアクションコード**には `USER.SELF_DELETE`（セルフサービスによるアカウント削除）と `USER.DELETE`（管理者による削除）が含まれます。

### エクスポート

**CSV をエクスポート**をクリックすると、現在フィルタリングされているビューを CSV ファイルとしてダウンロードできます。

**SIEM エクスポート（v1.0.4）** — `GET /api/admin/audit-logs/export?format=jsonl|cef` は、同じフィルタリング済みビューを SIEM に取り込み可能な形式（既定は JSON Lines、または ArcSight CEF）でストリーミングします。`AUDIT_LOG_EXPORT` 権限が必要で、エクスポート自体も `AUDIT_LOG.EXPORT` として記録されます。

v1.0.4 のアクションコードはフィルター UI で **モニタリング**（`MONITOR.*`）、**連携**（`JIRA.SETTINGS_UPDATE`）、**管理**（`ORG_DASHBOARD.VIEW`、`AUDIT_LOG.EXPORT`、`SNAPSHOT.IMPORT` / `SNAPSHOT.EXPORT` / `SNAPSHOT.WANTED_LIST_EXPORT`）、**キャッシュ**（`CACHE.UPDATE_TTL`、`CACHE.CLEAR`）としてグループ化され、新しいエクスポート・ゲートのコード（`SBOM.EXPORT`、`VEX.EXPORT`、`SARIF.EXPORT`、`COMPLIANCE_REPORT.VIEW`、`GATE.EVALUATE`、`GATE.GITHUB_PUBLISH`、`PROJECT.BATCH_PR`、`SBOM.IMPORT`、`COMPONENT.JIRA_TICKET`）も併せて提供されます。

### 保持期間

設定された保持期間より古い監査レコードは、スケジュールされたジョブによって自動的に削除されます。

| 設定キー | 既定値 | 説明 |
|---|---|---|
| `OSWL_AUDIT_RETENTION_MONTHS` | `6` | これより古いレコードは自動削除される月数 |
| `OSWL_AUDIT_MAX_PAGE_SIZE` | `200` | API 1 ページあたりの最大レコード数 |

`/org-dashboard` は、すべてのプロジェクトを 1 つのポートフォリオビューにまとめます — 深刻度の合計、最もリスクの高いプロジェクトのランキング、KEV 収載 CVE 件数、ライセンス警告。

## オフラインスナップショットバンドル（v1.0.4）

**設定 → 管理者 → オフラインスナップショット**

閉域網（エアギャップ）デプロイ（`OSWL_AIRGAPPED_ENABLED=true`）向けに、脆弱性・脅威インテリジェンスデータ（OSV、deps.dev、FIRST.org EPSS、CISA KEV）はライブ API ではなくインポート済みのスナップショットから提供されます — 外部への HTTP 通信は一切試みられず、スナップショットに存在しないコンポーネントは「データなし」として表示されます。

NVDの影響条件の根拠は、スナップショットの脆弱性行と保存スキャン判定の任意JSON文字列`nvdApplicability`に保持します。受信した`configurations`ツリーと存在する`id`・`sourceIdentifier`・`lastModified`・`vulnStatus`を含みます。configurationsと状態が両方なければフィールドはnullで、保存したメタデータ内でconfigurationsの欠落・空配列・明示的nullを区別します。取り込みだけで条件を評価したり候補を確定したりしません。文字列は出典の根拠であり、実行可能な内容や検証済みの影響判定ではありません。旧バンドルにはなく、旧エクスポーターは破棄する場合があります。既存の出典日付・サイズ制限・データ告知は引き続き適用します。

複数のCPE候補またはオフライン結果リストが同じNVD IDに異なる根拠を返す場合、提供元アダプターは未採点の確認候補1件と代替根拠一覧（nvdApplicability.conflictingRecords）を保持し、照会を未完了にします。JSONオブジェクトのキー順や照合信頼度の違いだけでは競合にしません。直列化した競合も後の読み取りで未確認を維持します。到着順や更新時刻で競合を解消せず、既存共有行を調整するものでもありません。

HTTPページの重複検出ではIDと保持するレコードを別々に追跡します。IDの重複は引き続き照会を未完了にし、同一ページ・後続ページ・一部破損したページの異なるレコードを提供元の競合確認に渡します。完全に同じレコードはその照会で1回だけ保持します。既存の共有行の調整や正とするrevisionの選択は行いません。

NVD提供元の結果では、保存IDが一致しlastModifiedを解析でき、未来でない場合に限りRejectedレコードを除外します。オフセットのないNVD時刻はUTCとして解釈します。不確かな取り下げ根拠はIDを保持し照会を未完了にし、古いスナップショットの未完了状態も維持します。configurationsがなくても状態・更新時刻を保持します。現在のNVD寄与結果のみをフィルターし、元のスナップショット・既存CVE・ほかの提供元の検出は削除しません。出典ごとの保存行の取り下げ・再有効化の調整は未実装です。

`SYSTEM_ADMIN` または `SETTINGS_SNAPSHOT_MANAGE` が必要です。[v1.0.4 の新機能](Whats-New-v1.0.4.md)を参照してください。

バンドルは v2 フォーマットです: 各 JSONL ファイルのチェックサムが `meta.json` に記録され、ソースごとの来歴情報（`bundleId`、`builtAt`、`asOf`、`origin`）も保存されます。チェックサムが一致しない場合、データを書き込む前にインポートが拒否されます。

スキャンのエクスポートには `meta.json.dataNotices` も含まれ、GitHub Advisory Database の帰属・ライセンスリンク、正規化の説明と適用範囲を示します。バンドル全体の再配布権限の証明や、提供されたレコード別の表示の完全な保存ではありません。再配布前に原典ごとの権限と表示の保存を確認し、GHSA alias だけで元の出典やライセンスを判断しないでください。

OSV 一括収集は、撤回状態や影響バージョンを判定する前に各原文の modified 時刻を確認します。欠落、解析不能、未来の時刻では収集を失敗として扱い、カバレッジを確定しません。オンライン・オフライン照会も同じ時刻検証を共有します。これは全スキーマ項目の妥当性や上流アーカイブの完全性を保証するものではありません。

V40 マイグレーションは永続スナップショット世代・ソースメタデータ・有効世代ポインターを追加します。最初のインポート試行で変更を適用する前に、既存ストアを基準世代として保持します。成功した反映では結果の payload と全ソースの日付・出典・供給された通知を新世代へコピーし、同じトランザクションでポインターを切り替えます。コピーやコミットに失敗すると以前の有効世代を保持します。過去の世代は ID で参照でき、後続の REPLACE・MERGE では書き換えません。初期実装は反映ごとに DB 内で全体をコピーし、履歴を自動削除しないため、保持世代数に応じた DB 容量が必要です。新アプリケーションの前に V40 を適用してください。旧版は履歴を管理しないため、その書き込みを追跡済み世代とみなしません。既存データの保持は追加の利用・再配布権を付与しません。

V41 はスキャンごとに選択したスナップショット世代 ID を記録する nullable 列を追加します。オフラインのデータ補完は条件付き DB 更新で有効世代を一度だけ選び、同時選択や古いオブジェクトの後続保存では変更できません。再試行も同じ世代を使用します。補完は共有ライブラリの照会キャッシュを迂回し、その世代の payload・未確認キー・ソース日付を読み取ります。KEV もグローバルキャッシュではなく固定したストアを使用します。オフライン修正対象検証は一連の検証で一つの有効世代を使用します。範囲は同期照会区間に限り、失敗時も解除・復元し、別 worker スレッドへ自動伝播しません。オフライン固定済みスキャンはオンライン補完で上書きできないため、そのモードでは新しいスキャンを開始します。新規オンラインスキャンの照会・キャッシュ動作は維持します。共有 Library/CVE 行や後続レポートは不変化されず、補完前の取り込みや独立 AI タスクも対象外です。履歴保持・rollback・不変の判定結果保存は残作業です。

スナップショットの反映は、別のトランザクション内から呼んだ場合も独立した SERIALIZABLE トランザクションでコミットします。同時 MERGE が以前に読んだ日付を使い、保持された古い行の基準日を新しく上書きすることを防ぎます。同時実行の競合では試行全体をロールバックし、検証済みの staging ファイルで合計 3 回まで再試行します。競合が続けば失敗となり、既存の 300 秒のトランザクション制限は各試行に適用されます。成功ログはコミット後に記録します。呼び出し元がロールバックしても、独立して完了した反映は取り消されません。別接続用の DB プール余裕が必要です。この変更は反映の整合性を保護するもので、永続世代・有効ポインター・スキャン全体の revision 固定は別作業です。

オフライン OSV・GitHub Advisory・NVD の照会バッチは、検出内容・未確認キー・ソース鮮度・候補有効期限をそれぞれ一つの独立した SERIALIZABLE トランザクションで読み取ります。同時インポートで旧世代の空の結果に新しいカバレッジや日付を付けることを防ぎます。GitHub Advisory・NVD の補完処理と GitHub の修正対象検証は、照会時に取得した完了状態を使用します。未完了の GitHub 証拠は検出内容と競合候補を保持し、修正バージョンを保留します。次の照会ではコミット済みの更新を取得できます。既存トランザクション内から呼ぶ場合、この短い照会には別の DB 接続が必要なため、同時読み取り用のプール余裕が必要です。この境界はソースごとの一つのバッチに限られ、スキャン全体・全ソースの統合照会・永続的なデータ世代固定は含みません。

オフライン deps.dev のバージョン・公示照会も、それぞれ独立した SERIALIZABLE トランザクションで本文とソース日付を読み取ります。バージョン照会には未確認コンポーネントキーも含めます。補完と修正対象検証は照会時の resolved/current 状態を使用するため、同時インポートで古い証拠が正常状態に変わることを防ぎます。未完了のバージョン証拠はライセンスと公示 ID を保持し、デフォルト・廃止・最新バージョン・scorecard の状態を保留します。deps.dev の二つの照会は別々であり、全ソースを一つのスキャン世代に固定する機能ではありません。

オフライン EPSS はスコアとソース鮮度を独立した SERIALIZABLE トランザクションで読み取り、古いスコアや日付のないスコアは未確認のままにします。KEV 更新は掲載一覧とソース日付の有効期限を一緒に読み取り、キャッシュに保持します。後のインポートの日付で以前のキャッシュの証拠を延長しません。確認済みの掲載情報は保持し、一覧にない ID はキャッシュの証拠が期限切れまたは日付不明なら未確認となります。既存の一日間のキャッシュ更新制限も適用されます。EPSS・KEV の照会はスキャン内の他ソースの照会とは別です。

照会結果に含まれる有効期限を補強処理から保存判定までそのまま渡し、後続のバンドル更新で以前の結果の寿命を延ばしません。オンラインではアドバイザリ判定開始時に 7 日の期限を設定し、オフラインでは元のソース日付に基づく期限を保持します。日付の根拠がなければ未確認のままとし、期限切れ候補は表示しません。既存の保存判定は自動再計算されないため、後続照会から取得した期限を置き換えるには判定を更新してください。DB 移行は不要です。

[OSV 仕様](https://ossf.github.io/osv-schema/#affectedpackage-field)に従い、パッケージ名 `*` は同じエコシステム内の全照会パッケージ名に適用します。提供されたオンライン原文・取込原文・一括収集で共通ですが、影響はバージョン範囲で判定し、範囲の欠落や未対応は未確認のまま保持します。共通修正候補はワイルドカードと個別パッケージの両方の制約を満たす必要があります。エコシステムやディストリビューションのリリースは区別し、`exam*` のような部分名はパターンと解釈しません。以前に欠落した検出を反映するには、既存の一括バンドルを再生成し、スキャン・照会キャッシュを更新してください。上流 API が該当する全アドバイザリを返すことを保証するものではありません。

一括収集は ZIP 中央ディレクトリが読み取れることを確認し、各原文エントリのサイズと CRC も照合します。途中で切れたアーカイブ、内容の不一致、原文ファイル名の重複は既存の出力バンドルを置き換えず収集を失敗させます。ダウンロード・キャッシュ・`--offline-sources` に適用します。圧縮アーカイブの一時コピーを検証し、成功・失敗時に削除するため、アーカイブ一つ分の一時ディスク容量が必要です。この構造検査は不完全または破損した ZIP を検出しますが、提供者のデータ自体の欠落や出所の真正性を保証しません。

同じ OSV 一括アーカイブ内で advisory ID が繰り返される場合、完全な JSON 内容が一致する必要があります。空白とオブジェクトのキー順は無視し、配列順は維持します。同一原文は一度だけ処理します。内容が衝突するとアーカイブ順に関係なく収集を中止し、既存の出力バンドルを保持します。全原文のメモリ保持に代えて ID ごとの SHA-256 ダイジェストを保存します。この整合性確認は出所の認証ではありません。

OSV の撤回は、時刻が有効で現在時刻以前の場合にのみ適用します。未来の時刻や不正な撤回情報ではカバレッジを未確認のまま保持します。オンライン・オフラインの原文照会は修正バージョンを提案せず advisory ID を保持し、一括収集は関連する照会範囲を未確認とします。有効な過去の撤回は従来どおり有効な脆弱性から除外します。

インポートは提供された dataNotices オブジェクトと平坦な upstreamDataNotices 配列をソースメタデータに保持します。マージは既存の通知と重複なく結合し、置換は対象ソースの通知を今回の通知に置き換えます。エクスポートは OsWL 自身の通知とともに保持したオブジェクトを upstreamDataNotices で渡します。これはインポート元の通知を保守的に含めるもので、レコード別の帰属対応や再配布の承認ではありません。繰り返す往復でも同一オブジェクトを重複・入れ子化しません。不正または読めない通知は処理を失敗させ、累積通知が 512 KiB を超える場合は通知を破棄せずインポートをロールバックします。過去に失われた通知は元のバンドルから再インポートしてください。配備前に V39 マイグレーションを適用してください。

`osv.jsonl` の脆弱性レコードには、元の OSV 文書を `osvAdvisory` JSON オブジェクトとして任意で追加できます。`id` は `osvId` と一致し、`modified` は有効な時刻、`affected` は配列である必要があります。保存時に credits・references を含む提供文書を保持し、オフライン照会では識別子・概要・CWE・深刻度・CVSSを原文から読み取り、影響範囲と修正バージョンを再評価します。共通の修正判定には関連する全レコードの原文と、新しく完了したソース照会の状態が必要です。原文のない既存レコードは従来の照会動作を維持しますが、共通修正の根拠にはなりません。このフィールドは原典の取得・再配布許可を付与しません。自動収集はまだ原文を保持しません。スキャンのエクスポートは下記の内容照合条件を満たす保存原文を引き継げます。元のバンドルを保管して権限と表示を別途確認してください。

アプリケーションは OSV 共通修正の判定・理由・アドバイザリ revision・現在影響を受ける ID/別名・排他的な有効期限を `libraries.osv_fix_assessment` に照会試行時刻とともに保持します。導入済みバージョンに影響しなくても更新先を制限する文書は revision の根拠に含まれます。画面と PR 候補の選択では、照会が完了し、保存済みの全検出に根拠があり、修正情報の競合がない有効な共通候補だけを使います。個別アドバイザリの修正情報は別途保持します。オンライン候補の表示期限は 7 日で、オフラインは元の OSV 基準日と設定済みの日単位の鮮度期間に従うため、再照会で古いデータの期限は延長されません。影響 ID や有効期限のない既存判定は更新まで未確認です。長期・永続キャッシュは消去してから再スキャンすると新しい根拠を取得できます。PR は作成直前に対象を再検証します。原文の自動収集は未完了です。

判定に使用した OSV 原文の SHA-256 内容ダイジェストも共通判定 JSON に保存します。オブジェクトのキー順と空白は無視し、配列順と内容は反映します。スキャンのエクスポートは、正確なコンポーネントキー、原文 ID 全体、更新時刻と内容ダイジェストが記録済み OSV 照会と一致し、対象 OSV 検出の根拠が揃い修正情報に衝突がない場合だけ保存原文を接続します。ダイジェストのない旧判定、欠落・追加・変更原文、失敗した照会では未確認原文を付けず従来の要約を保持します。原文には現在影響しない制約や credits・references も含めます。この出力は formatVersion 3 で、原文を再評価するインポーターが必要です。原文なしの出力は形式 2 を維持し、従来の形式 1・2 も引き続き取り込めます。行が 1 MiB の取込上限を超える場合、根拠を破棄せず出力を失敗させます。再出力はソース基準日を更新しません。ダイジェストは内容一致の根拠で、真正性や再配布権限の認証ではありません。既存の判定列を使用するため追加 DB 移行は不要ですが、ダイジェスト取得には旧判定の更新が必要です。

| 操作 | エンドポイント |
|---|---|
| バンドルの状態 | `GET /api/admin/snapshot` |
| インポート（ファイルアップロード） | `POST /api/admin/snapshot/import`（multipart、任意で `?mode=replace\|merge`） |
| インポート（サーバー上のパス） | `POST /api/admin/snapshot/import-from-path` |
| エクスポート | `GET /api/admin/snapshot/export` |
| ウォンテッドリスト | `GET /api/admin/snapshot/wanted-list` |

インポートはストリーミング処理され（アップロード全体をメモリにバッファリングしません）、`SNAPSHOT.IMPORT` として監査記録されます。エアギャップインスタンスでは、インポート直後にメモリ内の KEV カタログが再読み込みされ、新しいスナップショットが即座に適用されます。

### 定義のステータスと鮮度（staleness）

**定義ステータス（Definition Status）**カードには、ソースごとに 1 行が表示されます — `OSV`、`deps.dev (versions)`、`deps.dev (advisories)`、`FIRST.org EPSS`、`CISA KEV` — レコード数、アップストリームの**基準日（as-of）**、origin、インポート時刻とともに。タイトル横の鮮度バッジは（バンドルのビルド時刻やインポート時刻ではなく）**最も古い**ソースの基準日から計算されます:

| バッジ | 意味 |
|---|---|
| 最新（緑） | 最も古い定義が `staleness-warn-days` 以内 |
| 更新推奨（黄） | `staleness-warn-days` より古い |
| 古い（赤） | `staleness-critical-days` より古い |

| 設定キー | 環境変数 | 既定値 | 説明 |
|---|---|---|---|
| `oswl.airgapped.staleness-warn-days` | `OSWL_AIRGAPPED_STALENESS_WARN_DAYS` | `7` | 最も古い定義からこの日数を超えるとバッジが黄色になる |
| `oswl.airgapped.staleness-critical-days` | `OSWL_AIRGAPPED_STALENESS_CRITICAL_DAYS` | `30` | この日数を超えるとバッジが赤色になる |

ビルダーがウォンテッドリスト経由で要求されたものの、アップストリームで見つけられなかった、または確信を持って評価できなかったコンポーネントがある場合、**未解決（アップストリームデータなし）**行が表示されます — これらのコンポーネントは「確認済みでクリーン」ではなく「データなし」として扱ってください。

### インポートモード

- **バンドルの既定** — 差分（デルタ）としてビルドされた v2 バンドルは merge としてインポートされ、それ以外は replace としてインポートされます。
- **Replace** — バンドルに含まれる各ソースを書き込む前にクリアします。
- **Merge** — キーで upsert し、削除マーカー（tombstone）を尊重するため、デルタバンドルで失効したエントリを削除することもできます。

Merge ファイルで同じキーが繰り返される場合、最後のレコードが提供された原文を含む保存 payload 全体を置き換えます。内部バッチの境界に依存せず、異なる revision のフィールドは混合しません。削除マーカーは入力順に適用されます。

ファイルアップロードに加えて、**パスからインポート（Import from Path）**はサーバーのディスク上に既にあるバンドルを読み込みます。`oswl.airgapped.import-dir`（`OSWL_AIRGAPPED_IMPORT_DIR`）で設定したディレクトリ配下のファイルのみを受け付け、realpath チェックにより強制されます。値が空の場合、このエンドポイントは無効化されます。

### このインスタンス向けの定義をビルドする（ウォンテッドリスト）

**ウォンテッドリストをダウンロード**をクリックすると、このインスタンスがスキャンしたすべての一意な (ecosystem, name, version) の組み合わせが JSONL としてエクスポートされます。これにより、インターネットに接続されたマシン上の `oswl-vdb` ビルダーは、アップストリーム全体をミラーリングする代わりに、それらのコンポーネントだけの定義を取得できます。ファイルには ecosystem/name/version のみが含まれ — プロジェクト名、リポジトリ URL、ファイルパスは含まれません。インターネットに接続されたマシンで次を実行します:

```bash
scripts/oswl-vdb/oswl-vdb.sh build --wanted wanted-list.jsonl --sources osv,epss,kev,depsdev --out bundle.zip
```

（Windows では `oswl-vdb.ps1`）。その後、生成された `bundle.zip` をインポートカードでアップロードします。同じスクリプトは、インポート前にバンドルを確認するための `verify` と `inspect` サブコマンドも提供します。

## AI 設定

**設定 → AI**

CVE／ライセンス要約用の LLM プロバイダーとエンリッチメント動作を構成します。

| プロバイダー | 補足 |
|---|---|
| **無効** | AI インサイトは生成されない |
| **OpenAI** | API キー + モデル（例: `gpt-5.6-terra`） |
| **Anthropic** | API キー + モデル（例: `claude-opus-5`）。`temperature` の上書きは適用されません — 現行の Claude モデルはサンプリングパラメータを拒否するため、応答スタイルはプロンプトで調整されます |
| **Gemini** | API キー + 必要に応じて OpenAI 互換の base URL（例: `gemini-3.1-pro`） |
| **ローカル** | OpenAI 互換のエンドポイント（例: Ollama — ドロップダウンには `qwen3`、`gemma3`、`deepseek-r1` などの人気モデルタグが提案として表示） — または下記の内蔵 AI サイドカー |

各プロバイダーのモデル欄は自由入力コンボボックスです: ドロップダウンには現行モデルが提案として表示されますが、アカウントがアクセス可能な任意のモデル ID を直接入力できます。

内蔵 AI は別途インストールした llama.cpp を使用し、既定のダウンロードモデルは **Qwen3.5-2B Q4_K_M** です。**Gemma 4 E2B** は任意で手動インストールします。実行ファイルは `embedded-ai/llama/`、モデルは `embedded-ai/model/<系列>/` に配置します。起動時の事前取得はダウンロードのみで、サーバーの起動や LOCAL の有効化は行いません。既定の取得先は Hugging Face の固定リビジョンで、SHA-256 とサイズを検証します。既定の代替ミラーはなく、エアギャップモードではダウンロードしません。モデルを変更する場合は設定で停止し、モデルを選択・保存してから再度開始します。最新の要件と設定は[内蔵 AI](Embedded-AI.md)を参照してください。

同時に**アクティブ**にできるプロバイダーは 1 つだけです。タブには次も表示されます:

| 設定 | 用途 |
|---|---|
| プロンプトロケール（`en` / `ko` / `ja`） | `prompts.properties` か、韓国語・日本語のオーバーレイかを選択 |
| CVE／ライセンスのバッチ上限と深刻度 | スキャンごとのエンリッチメント AI 呼び出しを制限 |
| Temperature／最大トークン数／日次呼び出し上限 | LLM の挙動とコストのガードレール（Anthropic では temperature は無視されます — 上記参照） |
| 既定のデプロイメントプロファイル | プロジェクトにプロファイルがない場合の CVE トリアージ**および**ライセンスリスク評価の文脈 — 社内ツール、ネットワークサービス、配布されるソフトウェアでは義務が大きく異なります |
| プロンプトの上書き | キーごとのテンプレート編集（`GET /api/settings/ai/prompts` を参照） |

**接続テスト**はトークンを一切消費しません: 完了リクエストを送る代わりに、プロバイダーの利用可能なモデル一覧を取得するため（OpenAI/Gemini/Ollama は `GET {base}/models`、Anthropic は `GET /v1/models`）、認証情報と到達可能性の確認は無料であり、日次呼び出し上限にもカウントされません。設定されたモデル ID がアカウントでアクセス可能なモデルに含まれない場合、テストは成功しますが警告が表示されるため、タイプミスや未取得のローカルモデルを次回のスキャンではなくその場で発見できます。

**API:** `GET|PUT /api/settings/ai`、`POST /api/settings/ai/test-connection`、`POST /api/settings/ai/golden-test`。
**内蔵 AI:** `GET /api/settings/ai/embedded`、`POST .../embedded/start?model=`、`POST .../embedded/stop`、`PUT .../embedded/config` — [API リファレンス — AI](API-Reference.md#ai)を参照。
**プロジェクトごと:** `PATCH /api/projects/{id}/deployment-profile`。
**コンポーネント詳細:** CVE の AI 要約を再生成する `POST .../cves/{cveDbId}/ai-summarize`（`COMPONENT.CVE_AI_REGENERATE` として記録）。

### AI 応答のキャッシュ（v1.0.4）

CVE／ライセンスのバッチエンリッチメントは、各 `Cve` および `Library` 行に SHA-256 のコンテキストハッシュを保存します。次回のスキャン時、回答を左右する入力（severity、CVSS スコア／ベクター、修正バージョン、EPSS バケット、KEV ステータス、依存関係の種類、patchability、ライセンス名／ステータス、デプロイメントプロファイルなど）が変化していなければ、既存の AI 要約が再利用され、プロバイダーは再度呼び出されません。この動作は自動であり、AI 応答キャッシュをクリアする専用の管理画面はありません。コンポーネント詳細画面の **再生成** アクションを手動で実行すると、キャッシュを回避できます。

### 使用量とコストの追跡

AI カードには本日の呼び出し件数、トークン合計、推定コスト（`GET /api/settings/ai/usage`。日次集計テーブルに基づくため、履歴が増えても照会コストは低く抑えられます）に加え、10 件ずつページネーションされる**最近の呼び出し**表（`GET /api/settings/ai/usage/events`）が表示されます。生の呼び出しイベントは直近**100 件**のみ保持され、新しい呼び出しが記録されるたびに古いものから削除（FIFO）されますが、日次合計と 7 日間のトレンドは生のイベントログではなく集計テーブルから取得されるため影響を受けません。

推定コストはおおよその数値であり、プロバイダーからの請求書では**ありません**。各モデルの公式な 100 万トークンあたりの入力／出力定価を使って**モデルごと**に計算されます（例: `claude-opus-5`、`gpt-5.6-terra`、`gemini-3.1-pro` はそれぞれ異なる単価を持ち、同じプロバイダー内で 10 倍高価なモデルが 1 つの平均単価にまとめられることはもうありません）。キャッシュ入力・バッチ・ロングコンテキストの割引は反映されないため、目安として扱ってください。定価が公開されていないモデル（カスタムデプロイ、新規リリース、または**ローカル**プロバイダーで動作するもの全般）は、次のようなプロバイダーごとの固定単価にフォールバックします:

| 設定キー | 既定値（USD / 100万トークン） |
|---|---|
| `oswl.ai.pricing.openai-input-per-1m` / `openai-output-per-1m` | `2.50` / `10.00` |
| `oswl.ai.pricing.anthropic-input-per-1m` / `anthropic-output-per-1m` | `3.00` / `15.00` |
| `oswl.ai.pricing.gemini-input-per-1m` / `gemini-output-per-1m` | `1.25` / `5.00` |
| `oswl.ai.pricing.local-input-per-1m` / `local-output-per-1m` | `0` / `0` |

実際の契約単価が上記の既定値と異なる場合は、これらの値を更新してください。**ローカル**プロバイダーは、報告するモデル名にかかわらず常に設定された単価（既定 `0`）で見積もられます — 自己ホスト型のモデルには参照すべきトークン単価そのものが存在しないためです。

**設定 → キャッシュ**

**ライブラリエンリッチメントキャッシュ**（deps.dev + OSV）の一元的な制御ポイントです。個別の「外部 API 設定」画面や API はありません。

## SAML 2.0 SSO および SCIM 2.0 プロビジョニング

OsWL は、Okta、Entra ID、オンプレミス AD FS を利用する企業向けに SAML 2.0 シングルサインオンをサポートしています。SAML IdP が設定されると、`/login` に **SSO でサインイン** オプションが表示されます。

### SAML セットアップ

1. SP 署名鍵ペアを生成します（任意ですが推奨）:
   ```bash
   openssl req -x509 -newkey rsa:2048 -keyout oswl-saml-sp.key -out oswl-saml-sp.crt -nodes -days 3650 -subj "/CN=oswl"
   ```
2. `application-prod.yaml` の SAML ブロックのコメントを外し、環境変数を設定します:
   | 環境変数 | 用途 |
   |---|---|
   | `OSWL_SAML_IDP_METADATA_URL` | IdP メタデータ URL（例: Okta/Entra アプリメタデータ） |
   | `OSWL_SAML_IDP_CERTIFICATE` | IdP 署名証明書ファイルのパス |
   | `OSWL_SAML_SP_PRIVATE_KEY` | SP 秘密鍵ファイルのパス |
   | `OSWL_SAML_SP_CERTIFICATE` | SP 証明書ファイルのパス |
3. IdP に SP メタデータを登録します。メタデータエンドポイントは以下です:
   ```
   https://<your-oswl-host>/saml2/service-provider-metadata/oswl
   ```
4. IdP が email クレーム（NameID または `email`/`mail` 属性）を送信することを確認します。

> SAML ログインでは、IdP がすでにユーザーを認証しているため、メール OTP ステップをスキップします。既存の OsWL アカウントと一致しないメールアドレスは、SCIM が有効化してロールを割り当てられるよう、無効化されたローカルアカウントとして自動作成されます。

### SCIM 2.0 プロビジョニング

SCIM を使用すると、IdP のユーザー ライフサイクルを OsWL と同期できます。

| リソース | エンドポイント | 備考 |
|---|---|---|
| Users | `/scim/v2/Users` | GET/POST/PUT/PATCH/DELETE |
| Groups | `/scim/v2/Groups` | GET/POST/PUT/PATCH/DELETE |

**認証:** すべての SCIM リクエストに `Authorization: Bearer <scim_token>` を含める必要があります。専用 SCIM トークンは `ApiKeyService#issueScimToken` でプログラム的に発行します。SCIM トークンは `api_keys` テーブルに保存されますが、スコープは `SCIM` であり、通常の CLI スキャン API では拒否されます。

**グループ マッピング:** `oswl.scim.group-mapping`（環境変数: `OSWL_SCIM_GROUP_MAPPING`）で SCIM グループの表現方法を選択します:
- `TEAM`（既定）— 各 SCIM グループは Team になり、メンバーは TeamMember 行になります。
- `ROLE_TEMPLATE` — 各 SCIM グループは RoleTemplate になり、メンバーにはそのロール テンプレートが割り当てられます。

**ユーザー無効化:** `DELETE /scim/v2/Users/{id}` は OsWL 上で `active=false` に設定します。SCIM 経由ではユーザーを物理的に削除しないため、監査の帰属情報が保持されます。

**監査アクション:** SCIM 操作は `SCIM.USER_CREATE`、`SCIM.USER_UPDATE`、`SCIM.USER_DEACTIVATE`、`SCIM.GROUP_CREATE`、`SCIM.GROUP_UPDATE`、`SCIM.GROUP_DELETE`、`SCIM.GROUP_MEMBER_ADD`、`SCIM.GROUP_MEMBER_REMOVE`、`SCIM.AUTH_FAILURE`、`SCIM_KEY.CREATE` として記録されます。SAML ログイン イベントは `SAML.LOGIN_SUCCESS` および `SAML.LOGIN_FAILURE` として記録されます。

CLI の完全・差分バンドルにも `meta.json.dataNotices` を含めます。GitHub Advisory Database の資料がある場合の帰属、CC-BY-4.0 と出典へのリンク、保証の免責、選択・正規化・差分処理を説明します。インポートと再エクスポートは既存の通知保存経路でこの通知を保持します。CLI メタデータの欠落を補う変更であり、原文の全クレジットの保存、レコード別の権利特定、他の出典の利用許可を意味しません。[公式データベースライセンス](https://raw.githubusercontent.com/github/advisory-database/main/LICENSE.md) は 2026-09-13 に確認しました。OSV バルク収集はまだ原文の範囲根拠を省略するため、この通知だけで従来の要約レコードから共通修正バージョンを選べるようにはなりません。

VDB ビルダーの既定ソースは接続済みの `osv,epss,kev,depsdev` です。`--sources github-advisory` または `--sources nvd` を明示すると、混合指定も含め収集・出力置換前に失敗します。未使用の `--github-advisory-token`、`--github-api-base`、`--nvd-api-key` も拒否します。これらのコレクターはまだ CLI に接続されておらず、アプリのオンラインクライアントとスナップショットのインポート対応は CLI の収集対応を意味しません。以前は要求したソースが欠けたバンドルでも成功する可能性がありました。既存バンドルは実際のソース内容を確認してください。この変更は欠落レコードを補完しません。

VDB CLI の `--sources`・`--ecosystems` は空の値と空のカンマ区間を拒否します。先頭・末尾のカンマもエラーとし、各項目の前後の空白は除去して重複を入力順にまとめます。不正な一覧は収集前に停止し、既存の出力バンドルを保持します。カンマだけのソース指定で、何も収集せずにバンドルを正常に置換できた経路を遮断します。

差分の基準バンドルでは対応ソースの JSONL 行を厳密に読みます。不正 JSON、後続 JSON 値、重複フィールド、オブジェクト以外の行、欠落・文字列以外の識別子、重複レコードキーは読み飛ばしや上書きではなくビルド失敗にします。この失敗時は既存出力を保持し、空行は許可します。行の解析と識別子の一意性の検査であり、全レコードスキーマ、アーカイブの真正性、マニフェストのハッシュ、未選択ソースの保持の検証完了ではありません。

CLI バンドルは実際に実行したコレクターのソースファイルと基準日だけを含めます。差分モードの未選択ソースは省略し、削除マーカーを生成せず Merge インポートでもそのメタデータを置換しません。wanted 一覧のないビルドは以前の未確認コンポーネント根拠も保持します。選択したソースは従来どおり追加・変更・削除を計算します。選択ソース内で wanted 一覧やエコシステムフィルターを変更した場合の削除方針まで解決したものではありません。

差分の基準アーカイブは ZIP の中央ディレクトリを読み取れる必要があります。重複エントリー名、展開後のサイズ・CRC の不一致は出力置換前にビルドを失敗させます。切れたファイルと ZIP 以外も拒否します。破損や曖昧さの検査であり、CRC は提供元の認証やマニフェストのハッシュ・署名検証を代替しません。アーカイブの資源制限と完全なマニフェスト検証は別の残作業です。

`--since` の基準バンドルに `meta.json.mode` がある場合は `full` が必要です。差分ファイルは完全なソース状態ではなく変更分のため、そのまま次の基準にはできません。null・未知の値・文字列以外のモード、オブジェクト以外のメタデータ、重複 JSON フィールドと後続 JSON 値を拒否します。mode のない従来形式は読み取れますが、この互換性は完全性を証明しません。比較基準には完全なフルバンドルを使用してください。

差分比較の前に、基準マニフェストのデータファイル一覧・SHA-256・空白行を除く行数を実際のアーカイブと照合します。形式 2・3 はマニフェストが必須で、未対応・不正な形式バージョンは失敗します。従来の形式 1 またはバージョンなしでは省略できますが、提供されたマニフェストは検査します。不整合の検出であり、提供元の真正性や再配布権限の証明ではありません。

`oswl-vdb verify` は差分基準ローダーと ZIP・マニフェスト・対応 JSONL 行の整合性検査を共有します。チェックサムなしで成功しないよう明示的な files マニフェストを要求します。構造が正常な完全・差分バンドルは検証できますが、モードを宣言した差分比較基準は完全な状態が必要です。成功表示は整合性検査の結果であり、出典の真正性・完全な脆弱性カバレッジ・再配布許可を意味しません。

CLI wanted JSONL ローダーは不正・重複フィールド・後続 JSON を拒否し、空白以外の各行に ecosystem・name・version が空でない文字列のオブジェクトを要求します。不正行を要求範囲から黙って除外したり数値を文字列に変換したりせず、ビルドを失敗させます。空行は許可します。エコシステム別のバージョン妥当性は既存の収集判定が担当し、入力形式の検査だけで対応バージョンを確定しません。

KEV バルク収集は有効で未来ではない `dateReleased` 時刻を要求し、UTC の日付を保持します。欠落・不正・日付だけの入力はビルド日で置換せず収集失敗にします。2026-09-13 に確認した [CISA 公式スキーマ](https://raw.githubusercontent.com/cisagov/kev-data/main/known_exploited_vulnerabilities_schema.json) に従います。リリース時刻の検査であり、全カタログスキーマや再配布権限の検証ではありません。

KEV バルク収集は宣言された整数の件数を脆弱性配列の長さと照合し、空でないカタログバージョンを要求して、不正または重複する CVE 識別子を拒否します。不正行を捨てて部分成功のバンドルを作りません。オンラインクライアントの既存の一覧検証に合わせたもので、説明フィールド全体のスキーマとリリース間の巻き戻り・競合方針は別の範囲です。

オンライン KEV 更新とバルク収集は、入れ子も含む重複 JSON フィールドと後続 JSON 値を拒否します。オンラインは HTTP 変換で重複フィールドが先に失われないよう応答バイトを直接解析します。曖昧な入力から新しいカタログや確定した非掲載結果を作らず、既存のキャッシュ根拠方針を維持します。同じ合成入力をモック HTTP とオフラインソースファイルに適用して検査しました。

GHSA バルク収集ヘルパーは正常な 0 件検索を明示的なコンポーネントキーとして保持し、検索不能・失敗を `unresolvedKeys` で区別します。部分検索例外で得た脆弱性と修正バージョンの保留状態も保持します。未対応・未設定のクライアントには検索を送りません。このクラスはまだ CLI writer に接続されていないため、`--sources github-advisory` の有効化やバンドル出典追跡の完了ではありません。

GHSA のスナップショット変換では、競合する修正バージョン候補も保持します。競合がある場合は修正バージョンを確定せず、競合のない修正バージョンは維持します。JSON の保存・復元後もこの区別を保持します。未接続の CLI ソースを有効化する変更ではありません。

NVD の一括取得 helper は、スナップショット変換時に CPE 一致の信頼度と提供された適用条件の根拠を保持します。候補の取得失敗で他の候補の結果を破棄せず、部分応答の finding を保持し、コンポーネントを `unresolvedKeys` に記録します。正常な空応答は取得失敗や未対応のエコシステムと区別します。この helper はまだ CLI writer に接続されておらず、今回の変更は `--sources nvd` の有効化や再配布権の確認を意味しません。

コンポーネント単位の OSV/deps.dev 差分生成では、基準バンドルと現在のビルドの `wantedListId` が一致する必要があります。異なる場合や欠落している場合は、既存の出力を置き換える前に拒否します。インベントリの変更時や、このメタデータのない従来のバンドルには、新しい完全バンドルを生成してください。識別子は wanted ファイルの元のバイト列のハッシュなので、書式変更にも新しい完全な基準が必要です。KEV/EPSS のみの更新では wanted ファイルの一致を要求しません。この防御は、ソース別のエコシステム範囲や任意の部分マージにおけるレコード別の鮮度まで保証するものではありません。

KEV/EPSS のみを収集するビルドは、wanted ファイルが指定されてもパッケージの解析範囲や未確認レコードを生成しません。差分は選択したグローバルソースを更新し、既存のパッケージの未確認状態と関連ソースのメタデータを維持します。パッケージの解析範囲は OSV または deps.dev の収集を選択した場合のみ計算します。

CLI バンドルは、エコシステムのアーカイブ処理が正常に完了し、未確認の根拠がない具体的な wanted パッケージについて、空の OSV 結果行を保存します。これにより、正常な検出 0 件の照会をオフライン取り込み後も保持します。フィルターで除外したエコシステム、不正な識別子、未解釈の範囲を正常な空結果には変換せず、既存のソース基準日の期限検査を維持します。

スナップショットのコンポーネント識別子では、エコシステム、パッケージ名、バージョンに内部キー区切り文字 `|` を使用できません。このような識別子はオフライン照会で未確認となり、CLI の wanted 入力とスナップショット取り込みでは拒否されます。異なる座標が同じ保存キーに衝突することを防ぎます。正常な scoped npm 名、Maven 座標、ディストリビューションのバージョン区切り文字は既存のキーを維持します。

OSV と GitHub Advisory の照会識別子の検証にも、共通のスナップショットキー規則を適用します。`|` を含む曖昧な座標は、オンラインの空応答や完了済みスナップショットを根拠に正常な検出 0 件とは判定しません。正常な座標の照会動作は維持します。

ソースキャッシュは、未来の HTTP Last-Modified 時刻とローカルの日時メタデータの未来日付を、鮮度不明として扱います。有効な HTTP 時刻は UTC の暦日に変換して保存します。不明な日付をダウンロード日で置き換えず、OSV の収集は引き続き確認済みのソース基準日を必要とします。

EPSS の一括収集では、正規化した CVE 識別子を検証してからスコアを受け入れます。不正な識別子を黙って飛ばさず、収集を失敗させて既存の出力バンドルを保持します。小文字の識別子は正規化し、有効な長い CVE 連番も維持します。この検証は一括収集が対象であり、ライブ EPSS リクエスト処理全体の検証ではありません。

ライブ・オフラインの EPSS リクエストは、前後の空白と大文字小文字を正規化してから CVE 形式を検証し、重複を除去します。不正な識別子は HTTP とスナップショットの照会対象から除外し、スコア 0 で補完しません。応答に含まれるスコア 0 は有効な測定値として維持します。

ライブ EPSS 応答では、重複 JSON フィールドと末尾に追加された JSON 値を拒否します。曖昧な応答で最後のフィールド値を選択せず、そのバッチのスコアを未確認にします。他のバッチは独立して照会を続け、欠落したスコアを 0 に変換しません。

オフライン EPSS バンドルの取り込みでは、スコアと削除の両レコードについて正規化した CVE 識別子の形式を検証します。不正な識別子があれば REPLACE・MERGE のどちらでも取り込みを拒否し、既存のスコアとデータ基準日を保持します。スコア 0 と有効な長い CVE 連番は引き続き対応します。

OSV 一括収集では、入れ子を含む重複 JSON フィールドと末尾に追加された JSON 値を拒否します。曖昧なアドバイザリは、最後のフィールドでパッケージ・範囲・更新時刻・撤回の根拠を上書きせず、収集エラーとして扱います。CLI の収集失敗時は既存の出力バンドルを保持します。

OSV 一括収集は、主 GHSA ID とすべての affected 要素の GitHub Advisory Database 原文 URL が一致する場合に `osvAdvisory` 全体を保持します。公式リポジトリの `github-reviewed`・`unreviewed` JSON パスを対象とし、別名のみ、出典の欠落・混在、異なる ID・ホストには適用しません。提供されたクレジット・revision・範囲などを保持し、`dataNotices.githubAdvisoryDatabase.retainedOriginals` で ID と出典 URL を既存の CC-BY-4.0 表示に結び付けます。これは宣言された出典の識別であり、キャッシュの真正性確認や他の情報源の利用許可ではありません。対象レコードのオフライン共通修正候補の根拠を保持しますが、他の情報源と配布プロファイルの制御は未完了です。アプリのエクスポートは取り込み行全体ではなくスキャン済みライブラリが対象です。
