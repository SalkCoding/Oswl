# セキュリティセンター

保存済みの照会結果と OSV 共通修正判定は、ネスト内を含む JSON 重複キー、後続の JSON 値、数値・真偽値からテキストへの暗黙変換を拒否します。曖昧な照会結果は STORAGE/UNAVAILABLE、共通修正判定は STORAGE_ERROR として扱い、共通修正バージョンを提示しません。読み取りだけでは元の保存文字列や個別検出の修正情報を変更しませんが、後の成功した照会は現在のキャッシュを更新できます。

オンラインの GitHub Advisory 応答も、ページを解釈する前に重複 JSON フィールドと末尾の追加 JSON 値を拒否します。曖昧なページは照会未完了として扱います。前のページで独立に確認した脆弱性は保持し、照会全体が未完了のため修正候補は保留します。提供元応答の真正性を認証したり、オフラインスナップショットの解釈を変更したりする機能ではありません。 同じアドバイザリが同一ページまたは複数ページで有効・撤回状態の矛盾を示す場合、照会を未完了とし修正候補を保留します。有効な応答で観測した検出は保持し、矛盾する状態から現在のrevisionを選びません。一貫して撤回済みの項目は引き続き除外します。 npm・Cargo・Go・PyPI・Maven・NuGetでは、オンラインの空応答や完了済みの空スナップショットを照会完了とする前に、既存の生態系別比較器でインストール済みバージョンを検証します。未対応の具体的バージョン構文は、公示がなくても未確認のままです。他の生態系のバージョン順序対応を追加する変更ではありません。 OSVもnpm・Cargo/crates.io・Go・PyPI・Maven・NuGetの具体的バージョン構文を検査してから照会完了を判定し、オンラインやスナップショットの空結果にも適用します。対応する構文が不正なら個別・共通の修正案内を保留し、利用可能な検出とスナップショットの元の候補は保持します。出典の鮮度とは別の検査であり、他の生態系の比較器を追加しません。 OSVのバッチ・後続ページ・公示詳細応答は、解釈前に重複JSONフィールドと末尾の追加JSON値を拒否します。読み取れない最初のバッチは未完了とし、詳細の失敗時は照会した公示IDだけを保持します。後続ページの失敗では先に確認した検出と個別根拠を保持しますが、共通修正バージョンと照会完了判定は保留します。

GitHub Advisory の照会が完了した場合、インストール済みバージョンを含まない範囲も含め、同じアドバイザリの検証済み全範囲から提供元の修正候補を検討します。候補はインストール済みバージョンより新しく、そのアドバイザリの収集済み全範囲を外れている必要があります。例えば2.0.0が別の区間で影響を受けても、提供元の3.0.0が全区間を外れるなら候補として保持します。影響のない区間をインストール済みの検出項目に追加したり、パッケージ全体の安全な更新先を確定したりはしません。[GitHubのフィールド定義](https://docs.github.com/en/graphql/reference/security-advisories#securityvulnerability)を参照してください。

DB統合検査ではオンラインクライアントに合成した重複範囲を渡し、選択結果を明示的なテストZIPにしてH2および独立したPostgreSQL DBへ取り込み、オフラインクライアントで照会します。新しい基準日では同じアドバイザリ・深刻度・修正バージョン3.0.0を保持します。8日経過または基準日欠落では検出と保存候補を保持しつつオフラインの修正案内を保留し、存在しないバージョンキーを照会完了としません。日付は模擬条件です。importer/client経路の検証であり、CLI収集・実際のGitHub接続の検証ではありません。

パッチフィルターはコンポーネント/ライブラリ ID を一度並べ替え、必要な証拠フィールドをバッチ取得して選択ページのコンポーネントエンティティだけを読み込みます。表示とフィルターは照会時刻・パッチ判定規則を共有し、未確認の照会、CPE 候補、深刻度欠落、空白だけの修正バージョンを同じように扱います。各コンポーネントに検出項目1件を持つ50,000件のローカル H2 単一測定では、エンティティ読み込みは約10万件から1～305件となり、25,000件の一致結果を1.1～1.8秒で正確にページ分割しました。インメモリ DB を含む JVM 全体の測定ヒープは512MiBの上限に対して約460MiBでした。個別の観測値であり、本番の遅延パーセンタイルやメモリ保証ではありません。同時リクエスト、多数の検出項目を持つライブラリ、本番 PostgreSQL 規模は追加検証が必要です。

追加のローカル H2 検査では5,000個のコンポーネントに各10件の検出項目を置き、ページ0・1・24・25を読むサービス呼び出し4本を同時実行しました。各呼び出しの一致総数は2,500件で、空でない3ページの300個に重複はありませんでした。CPE 候補1件とパッケージ証拠9件が混在するライブラリもパッチ可能の結果から除外されました。単一実行の所要時間は5.0～5.3秒、総エンティティ読み込みは3,608件、JVM 全体の測定ヒープは約379MiBでした。HTTP 同時リクエスト、本番 PostgreSQL 性能、同時更新を保証する検査ではありません。

深刻度フィルターは表示件数と同様に CPE 候補を除外し、未評価フィルターには深刻度の欠落と NONE を含めます。深刻度フィルターを選択しなければ候補も表示されます。パッチフィルターはコンポーネント行と同じ判定を使用します。照会未完了または CPE 候補がある場合はパッチ可能・不可能の結果に含めず、深刻度の欠落だけで個別の修正情報を除外しません。バージョン状態フィルターは検出項目のないコンポーネントに適用します。パッチ可能は個別の修正情報があることを示し、共通の安全な更新先を証明しません。パッチフィルター選択時は、他の条件を満たす行を100件ずつ評価してから要求ページと正確な総件数を計算するため、大規模スキャンでは照会コストが増える場合があります。リスク順は候補を除く重大・高・中・低・未評価の件数を順に降順で比較し、続いて CPE 候補数を比較します。同順位は名前とコンポーネント ID で決めます。低い深刻度の件数が多くても、より高い深刻度の件数より優先されません。候補は引き続き表示しますが、元の深刻度で深刻度集計の順位を上げません。順位の値が0でも照会完了や安全を証明しません。

コンポーネント表・詳細ヘッダー・印刷表・CSV の深刻度集計でも CPE 候補を除外し、候補数を別に表示します。候補のみの場合はパッチ可否を未確認とし、脆弱性なしのバッジを表示しません。深刻度の欠落と NONE は未評価として集計します。CSV は既存の列の後に `CPE Match Review Candidates` を追加するため、列数を固定した連携は更新が必要です。これらのコンポーネント表示は引き続き共有ライブラリキャッシュを参照し、保存済みの過去の集計と異なる場合があります。

スキャン概要の深刻度集計と組織KEV集計は、照合の確認が必要なCPE候補を除外します。セキュリティセンター・プロジェクトカード・組織画面・リスク推移では候補数を別表示します。同じ検出にパッケージ根拠があれば既存の分類を維持します。V45は新しいアーカイブに候補数を保存します。保存済み判定や候補数のない過去のアーカイブは元の集計を維持し区分不明を表示し、推測による再分類や0への置換は行いません。詳細行の分類や現在の共有キャッシュと過去データの違いは、この概要集計とは別の範囲です。

脆弱性の照会が未完了の場合、パッチ可否は不明のままとし、個別の脆弱性と保存された修正バージョンは表示を維持します。照会完了時のパッチ可能は有効な検出の一部に修正バージョンが記録されているという意味で、一つのバージョンで全検出が解決する保証ではありません。パッチ不可は有効な検出に修正バージョンが記録されていないという意味で、提供元に修正が存在しない証明ではありません。共通アップグレードの推奨は別途検証します。

スキャン根拠の案内には選択したスキャンID、記録日時、登録リポジトリが表示されます。当時の判定が保存されていない以前の記録だけでは、サンプル・手動送信・実際のリポジトリスキャンを区別できません。0件を正常なスキャンの証拠にせず、実際のリポジトリのQuick Importまたは新しいCLIスキャンで確認してください。コンポーネント詳細は現在の共有照会キャッシュを表示し、当時の結果とは異なる場合があります。判定の保存は全出典の照会成功を保証しません。

セキュリティセンターは OsWL における主要な脆弱性管理インターフェースです。プロジェクトの最新スキャンで検出されたコンポーネントに影響するすべての CVE を、フィルタリング・ソート可能な一覧として提供します。

URL: `/projects/{id}/security-center`

**アクセス:** `SECURITY_CENTER_VIEW`（またはシステム管理者）**および** [プロジェクトメンバーシップ](Authorization-Layers.md)が必要です。エクスポートと印刷には `SECURITY_CENTER_EXPORT`、状態変更には `SECURITY_CENTER_UPDATE_STATUS` が必要です。

## CVE 一覧の見方

セキュリティセンターの各行は、スキャンされたコンポーネントに紐づく 1 件の **CVE**（Common Vulnerabilities and Exposures）エントリを表します。

| カラム | 説明 |
|---|---|
| **コンポーネント** | ライブラリ名とバージョン |
| **エコシステム** | パッケージエコシステム（MAVEN、NPM、PYPI など） |
| **CVE ID** | deps.dev/OSV による CVE または GHSA 識別子（例: `CVE-2021-44228`） |
| **CVSS スコア** | 数値の深刻度スコア（0.0〜10.0） |
| **深刻度** | CRITICAL / HIGH / MEDIUM / LOW |
| **修正バージョン** | 推奨される修正バージョン（判明している場合） |
| **状態** | 現在のトリアージ状態 |
| **パッチ適用可否** | 修正が利用可能かどうか |

---

## 深刻度レベル

OsWL は標準的な CVSS 3.x の範囲を使って CVSS ベーススコアを深刻度区分にマッピングします。

| 深刻度 | CVSS スコア範囲 | 意味 |
|---|---|---|
| **CRITICAL** | 9.0〜10.0 | リモートから悪用可能で影響大 — 直ちに修正 |
| **HIGH** | 7.0〜8.9 | 深刻なリスク — 今スプリントで優先対応 |
| **MEDIUM** | 4.0〜6.9 | 中程度のリスク — 近いうちに修正 |
| **LOW** | 0.1〜3.9 | 軽微なリスク — 都合の良いタイミングで修正 |
| **NONE** | 0.0 | 情報提供のみ／有効なスコアなし |

## CVE ステータスのライフサイクル

プロジェクト内の各 CVE には、次のいずれかのステータスを割り当てられます。

| ステータス | 意味 |
|---|---|
| **OPEN** | 新規検出 — レビューが必要 |
| **IN_PROGRESS** | 対応中 |
| **SUPPRESSED** | リスクを認識済み。この文脈では当面の優先対応ではない |
| **FALSE_POSITIVE** | 該当しないことを確認済み（例: 脆弱なコードパスに到達しない） |
| **RESOLVED** | 修正済み — アップグレード適用またはコンポーネント削除 |

> ステータス更新に必要な権限: `SECURITY_CENTER_UPDATE_STATUS` またはシステム管理者。

## フィルタリングとソート

セキュリティセンター上部のフィルターバーで一覧を絞り込めます:

* **深刻度** — CRITICAL / HIGH / MEDIUM / LOW
* **状態** — OPEN / IN_PROGRESS / SUPPRESSED / FALSE_POSITIVE / RESOLVED
* **エコシステム** — MAVEN / NPM / PYPI など
* **パッチ適用可否** — Patchable / Non-Patchable / Unknown
* **検索** — CVE ID とコンポーネント名にまたがるフリーテキスト検索

任意のカラムヘッダーをクリックすると昇順／降順でソートできます。専用の**並び替え**セレクターは基本の並び順を制御します: **リスク（既定）**（深刻度の高い順）、**名前**、または**ライセンスリスク**。

## 一括ステータス更新

1. チェックボックスで 1 件以上の CVE を選択します。
2. アクションツールバーの**ステータス更新**をクリックします。
3. ドロップダウンから新しいステータスを選択します。
4. 確定します。

選択したすべての CVE が単一のトランザクションで更新されます。

## エクスポート（v1.0.4）

アクションツールバーの**エクスポート**ドロップダウンは、最新の完了スキャンから標準準拠の成果物を生成します:

| 項目 | エンドポイント | 形式 |
|---|---|---|
| SBOM（CycloneDX） | `GET /api/projects/{projectId}/sbom` | CycloneDX 1.6 JSON |
| VEX | `GET /api/projects/{projectId}/vex` | CycloneDX VEX — トリアージ判断を反映 |
| SARIF | `GET /api/projects/{projectId}/sarif` | SARIF 2.1.0、GitHub コードスキャンにアップロード可能 |
| コンプライアンスレポート | `GET /projects/{projectId}/security-center/compliance-report` | 印刷用 HTML（*印刷 → PDF として保存*を使用） |
| CVE／ライセンス CSV | — | 選択した完了スキャンのコンポーネント概要（既定: 最新の完了スキャン） |

コンポーネント CSV は既存の列の後に `Vulnerability Lookup Complete`、`Lookup Outcomes`、`Lookup Attempt At` を追加します。`No` の場合、CVE 0 件だけでは照会完了と判断できません。`Yes` はコンポーネント画面と同じ完了基準であり、安全性を保証しません。ソース別の結果は名前順の `SOURCE=STATUS` ペアで表示し、存在しない過去のメタデータは空欄にします。ソース別の結果がないレガシーキャッシュは取得時刻があっても `No` です。永続キャッシュ設定でも次の解析で再照会します。照会時刻は保存されたローカル時刻であり、脆弱性データの公開日や鮮度の保証ではありません。列数を固定した利用側は、追加された三つの列に対応する必要があります。

一括操作には**アップグレード PR を作成**も含まれます。選択したすべてのコンポーネントを修正バージョンに引き上げる単一のプルリクエストを作成します。

詳細は[v1.0.4 の新機能](Whats-New-v1.0.4.md)を参照してください。

## エアギャップ（オフライン）モード

OsWL がエアギャップ（オフライン）モードで実行されている場合、セキュリティセンターの一覧画面、印刷用セキュリティレポート、コンプライアンスレポートの上部に **オフライン定義の基準日** バナーが表示されます。

> オフラインモード — 2026-07-24 時点の脆弱性定義で分析された結果です。

日付は読み込んだオフラインスナップショットの上流ソース基準日のうち最も古いもの（OSV、deps.dev advisory/バージョン、EPSS、CISA KEV）です。スキャン時点の脆弱性データがどれだけ新鮮だったかを監査証跡で確認できるように表示されます。定義の鮮度しきい値とスナップショットの取り込みは **設定 → 管理 → オフラインスナップショット** から管理します。

## コンポーネント詳細

コンポーネント名をクリックすると**コンポーネント詳細**サイドパネルが開き、次が表示されます:

脆弱性があり、現在のバージョンと異なる文書化された修正対象を選べない場合、自動 PR 作成は最新リリースで代替しません。最新であることはセキュリティ修正の証明にはなりません。最新リリースへの通常の更新 PR は、CVE がなく古いバージョンだと確認された場合に限り、バージョン状態が不明な場合は許可しません。

単一・一括 PR の VCS 変更直前に、OSV で導入済みと提案先のバージョンを再照会します。セキュリティ修正先は現在の OSV 原文に基づく共通修正と一致し、保存済みの検出に根拠があり、修正情報に競合がないことが必要です。対象の OSV 結果は空であり、deps.dev のバージョン照会も完了してアドバイザリ ID がない必要があります。GitHub Advisory が設定済み、または以前に必要だった場合は、その照会も完全な空の結果が必要です。オフラインでは対象バージョンのスナップショット項目が必要で、欠落・古いデータでは PR を保留します。CPE・リポジトリの識別や対応するバージョン根拠がないエコシステムは未検証です。この確認はパッケージバージョンと照会したソースの範囲であり、更新後の依存関係グラフ全体を検証しません。画面と PR 候補の選択は、深刻度の高い個別修正ではなく現在有効な OSV 共通判定を使用します。根拠の欠落・期限切れ・照会未完了・検出の根拠不足・競合がある場合は共通候補を未確認とし、個別の修正情報を保持します。共通候補も作成直前の対象確認で拒否される場合があります。

* deps.dev のプロジェクトレコードから取得した、そのライブラリが実際に何であるかの簡単な説明、およびホームページ／ソースリポジトリへのリンク
* そのライブラリのすべての CVE（CVSS の詳細分析を含む）— 上部のバッジとは区別された**セキュリティ課題（Security Issues）**見出しの下にグループ化
* ライセンス名とコンプライアンス状態
* AI 生成のライセンスリスク要約
* 最新の利用可能バージョンと非推奨通知
* 完全な依存関係パス（直接 vs. 推移的）
* サプライチェーンヒューリスティックがパッケージを検出した場合の **OpenSSF Scorecard** スコア、**既知の悪性** / **タイポスクワッティングリスク**バッジ（v1.0.4）
* Jira 連携が設定されている場合の**Jira 課題を作成**ボタン（v1.0.4）。作成後はバッジが直接 Jira の課題にリンクし、作成に失敗した場合はアプリの他の箇所と同じスタイルのトーストで理由が表示されます

長い CVE の説明は折りたたまれた行では省略されますが、行をクリックすると展開されアドバイザリの全文が表示されるため、*なぜ*それが脆弱性なのかを常に確認できます。

パネルには対応アクションもあります: **パッチを適用（PR を作成）**と**保留**です。保留には理由と有効期限プリセット（1 週間 / 1 / 3 / 6 か月、カスタム日付、または無期限）を記録します。カスタム有効期限は**未来の日付**でなければなりません — 過去の日付や不正な形式は HTTP 400 で拒否され、日付ピッカーでも明日以降しか選択できません。

PR/MR が作成されると、成功パネルに目立つ**PR/MR を見る**ボタンと、折りたたみ可能な**「変更内容は？」**要約（パッチ済みのマニフェストファイルパスとバージョンの引き上げ、例: `pom.xml`: `log4j-core 2.14.1 → 2.17.0`）が表示されます。

コンポーネントの保留期間が切れると（夜間スケジューラーにより）、保留は解除され、セキュリティセンターには保留が過去 7 日以内に終了したコンポーネントに対して閉じることのできる**🦉フクロウのリマインダーバナー**が表示され、再レビューを促します。

## AI セキュリティインサイト

AI プロバイダーが設定されている場合（**設定 → AI**）、スキャンのエンリッチメントで自由記述の AI インサイトが生成されます。v1.0.4 以降、スキャンレベルのインサイトはすべてスキャンごとの 1 回の統合 AI 呼び出しで生成されます:

* **セキュリティポスチャーインサイト** — 現在の CVE 件数と深刻度分布の総合評価。セキュリティセンター上部に 1 段落の **AI Insight** 要約として表示
* **セキュリティリスクトレンドインサイト** — 前回スキャンとの比較による改善・悪化の傾向。[リスクトレンド](Risk-Trend.md)ページに表示

インサイトはスキャンごとに 1 回生成されます。AI プロバイダーを初めて有効化すると不足分が自動補完され、AI プロンプトの言語を変更すると最近のスキャンのインサイトが再生成されます。また、ライセンスページから手動で再生成することもできます。

## パッチ適用可否

OsWL はライブラリのすべての CVE にまたがる `fixVersion` フィールドからパッチ適用可否を導出します:

| 状態 | 条件 |
|---|---|
| **PATCHABLE** | 少なくとも 1 件の CVE に既知の修正バージョンがある |
| **NON_PATCHABLE** | CVE は存在するが、既知の修正がない |
| **UNKNOWN** | CVE がない、または CVE データがまだエンリッチされていない |

## データソース

CVE データは 2 つのソースから取得され統合されます:

* **deps.dev** — `GetAdvisory` による GHSA アドバイザリ、CVE エイリアス、CVSS スコア、タイトル
* **OSV**（Open Source Vulnerabilities） — `POST https://api.osv.dev/v1/querybatch` による概要、修正バージョン、**CWE ID**（`database_specific.cwe_ids`）

OSV が提供する場合、CWE 識別子（例: `CWE-79`）はコンポーネント詳細パネルに表示されます。

v1.0.4 以降、優先順位付けのための 2 つのフィードも統合されています:

* **CISA KEV** — *Known Exploited Vulnerabilities* カタログ。KEV への収載は実際に悪用が確認されていることを意味し、トリアージ順では生の CVSS スコアより優先されます。
* **EPSS**（FIRST.org） — 今後 30 日間の悪用確率で、KEV に載っていないすべての項目の優先順位付けに使われます。

テスト・開発専用の依存関係はその scope でタグ付けされ、一覧から隠して本番リスクを際立たせることができます。除外ではなくタグ付けなので、SBOM から何かが消えることはありません。

エンリッチメントは各スキャン後に自動実行され、**設定 → キャッシュ**（`/api/settings/cache`）のキャッシュポリシーに従って更新されます。

## 内蔵ソース解析の完全性

シークレット・IaCのファイル読み取りまたはディレクトリ走査に失敗した場合、収集済みの検出と共に未完了マーカーを保持します。シークレットルールがない場合も未完了とします。既存のマーカー種別は、シークレット検出によるブロックが無効でもゲートの完了判定を防ぎます。読み取り可能な空ディレクトリは引き続き0件を返します。全ての除外ファイル・解析予算・無効化されたスキャナー・他の取り込み経路のソース欠落に対応したものではありません。 内蔵スキャナーの検出上限300件に達した場合、保持した検出とは別に未完了マーカーを1件記録します。ちょうど300件でも、その時点で停止し全入力の末尾まで検査したことを確認できないため未完了とします。収集済みの検出は削除しません。

解析対象ファイルが1,000,000バイトを超える場合も、黙って0件を返す代わりに未完了を記録します。上限以下のファイルは引き続き解析します。既存のバイナリ拡張子の除外とIaC対象の分類を適用してからサイズを確認します。これはファイル単位の制限であり、総バイト数と時間の予算は別の残作業です。

シークレット解析は、不正または途中で切れたUTF-8入力を未完了として扱います。不正なバイトを置換文字に変えて読み取り成功とはしません。他の読み取り可能なファイルの検出結果は保持します。置換文字自体を正しく符号化した場合を含め、正常なUTF-8は読み取れます。他の文字エンコーディングを自動的に推測したり変換したりはしません。

拡張子の除外を通過したファイルでNUL文字によりシークレット解析が停止した場合、未完了として記録します。それまでの検出結果は保持し、未読の残りを検査済みとは扱いません。既存のバイナリ拡張子の除外方針は維持します。

## Pythonパッケージの照会識別子

OSVの応答に検出項目がなくても、既存のPythonパッケージ名の検証を適用します。不正な名前はオンライン・オフラインとも照会未完了とします。保存済みの検出項目は不完全な証拠として保持しますが、修正バージョンの案内は保留し、保存した候補は変更しません。正常な区切り文字の組み合わせと1文字の名前は引き続き許可します。規則は[PyPAの名前仕様](https://packaging.python.org/en/latest/specifications/name-normalization/)に従い、意図したパッケージを推測して不正な名前を補正しません。

OSV bulk収集も照会と同じ識別子検証を使い、npm/Cargo・Go・Python・Maven・NuGetのバージョンと既存のパッケージ名規則を確認します。アドバイザリに登場しない不正な要求も未解決とし、正常な要求の収集は継続します。未解決キーを作れないほど識別子が欠けている場合は収集を失敗させます。他のエコシステムのバージョン比較器を追加する変更ではありません。CLIは該当する要求をunresolved.jsonlに保持します。

バンドル生成時、OSVが明示的に未解決とした結果は、他のOSVアドバイザリに検出項目がある場合やdeps.devにパッケージ情報がある場合も未解決のまま保持します。確認済みの検出項目は削除せず、unresolved.jsonlと共に保持します。収集時の不確実性を維持する変更であり、全ての供給元別の完全性モデルを完成させるものではありません。

ローカルCLI → H2取り込み → オフラインOSV照会で、全体バンドル後の差分更新による明示的な未解決と収集完了の双方向の切り替えを検証しました。検出項目と個別の修正候補を保持しながら未解決マーカーが追加・削除されます。現在のbulk CLIレコードはアドバイザリ範囲の原文を省くため、照会完了でも共通修正はNO_RANGE_EVIDENCEで保留し、未解決照会ではINCOMPLETE_LOOKUPで保留します。この制約はオンラインとオフラインの修正判定の完全な同等性を証明するものではありません。

ディストリビューションのbulkダウンロードは[OSVのエコシステム名の案内](https://google.github.io/osv.dev/data/#ecosystem-naming)に従い、Debian・Alpine・Ubuntuの親バケットを使用します。アドバイザリの照合にはリリース識別子を維持し、別のリリースと混同しません。2026-09-13の各all.zipへのHEAD要求でHTTP 200とLast-Modifiedの日付2026-09-12を確認しました。応答ヘッダーのみの確認であり、データ全体の完全性や再配布権限を検証したものではありません。旧リリース別のオフラインソースキャッシュは現在の親バケット名で準備する必要があります。

リリース別Alpineの照会とbulk収集も、空の結果を完了とする前に既存のAPKバージョンパーサーを適用します。*やlatestなど未対応の入力は未解決とし、対応するrevision・プレリリース形式は引き続き許可します。キャッシュの検出IDは保持しますが、不正な入力には修正バージョンを案内しません。既存パーサーの対応範囲を使う変更であり、Debian・RPMのバージョン比較を追加するものではありません。

APKの数字部分の表記を保持し、最初の部分以降に先頭ゼロがある場合の順序を反映します。[apk-toolsのバージョン実装](https://raw.githubusercontent.com/alpinelinux/apk-tools/master/src/version.c)と[文字列整列実装](https://raw.githubusercontent.com/alpinelinux/apk-tools/master/src/blob.c)で確認した動作に基づきます。比較器はAlpine:と内部ALPINE:の両方を認識し、パッケージ・リリース照合は別に維持します。合成テストで比較・影響範囲・bulk修正候補の選択を検証しました。GPL-2.0-onlyの上流ソースは動作確認のみで複製・同梱せず、native apk実行や全体の文法同等性を検証したものではありません。

APK比較では数字部分・suffix番号・revisionの省略と明示的な0も区別します。例えば1は1.0より、1.0は1.0-r0より前になります。明示されたrevision番号0と00は数値的に同じままです。上記の上流実装のトークン順序を基に、直接比較とアドバイザリ範囲・修正候補の選択を検証しました。native APKとの完全な同等性は未検証です。

APKパーサーはv/V接頭辞や前後の空白を除去せず、suffixにはunderscoreを要求します。1.0p1・1.0rc1を1.0_p1・1.0_rc1へ黙って変換しません。末尾の1文字は有効な文法として維持し、suffixと区別します。供給元の未対応表記を同じバージョンの別名と確定せず、不確実なまま保持します。上記の上流文法に基づきますが、文法全体の対応は未完了です。
