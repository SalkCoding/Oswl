# 권한 레이어 (Authorization layers)

**대상 독자:** 개발자, 보안 담당자, 라이선스·컴플라이언스 담당자, IT 운영, 경영·의사결정권자 — 소스 코드 없이 OsWL에서 *누가 무엇을 할 수 있는지* 이해하려는 분들.

---

## 한 줄 요약

OsWL에는 **서로 다른 세 가지 개념**이 있습니다. 일상 언어에서는 비슷하게 들리지만(“관리자”, “역할”, “멤버”) 제품 안에서는 다릅니다.

| 구분 | 쉬운 이름 | 답하는 질문 |
|------|-----------|-------------|
| **A** | **역할 템플릿** (인스턴스 전역) | “이 사람이 스캔 제출, 라이선스 내보내기, 설정 메뉴 등을 쓸 수 있나?” |
| **B** | **프로젝트 멤버십** | “이 사람이 **이 프로젝트** 데이터를 열 수 있나?” |
| **C** | **시스템 관리자** | “이 사람이 OsWL 전체(사용자, 감사 로그, 모든 프로젝트)를 운영할 수 있나?” |

일반 사용자가 특정 프로젝트에서 일하려면 보통 **A와 B가 모두** 필요합니다.

- **A** — 예: 라이선스 페이지를 보려면 `LICENSE_VIEW`  
- **B** — 해당 프로젝트의 `project_members`에 등록  

**시스템 관리자(C)** 는 멤버십과 관계없이 모든 프로젝트에 접근할 수 있습니다(지원·거버넌스).

> **개발자용 표현:** 코드·문서에서는 “역할”만 쓰지 말고 **역할 템플릿(Role template)**. **프로젝트 멤버십**이라고 부르고, 프로젝트의 `ADMIN` 멤버 타입과 혼동하지 않도록 합니다.

---

## 레이어 A — 역할 템플릿 (Admin / Developer / Viewer)

- **설정 → 관리자 → 역할 템플릿**에서 구성합니다.
- 사용자 초대·편집 시 지정합니다.
- **권한(Permission)** 묶음으로 구현됩니다 (예: `SCAN_SUBMIT`, `SECURITY_CENTER_VIEW`).
- 권한 목록에는 **인스턴스 관리 기능**도 포함됩니다 (v1.0.4에서 추가된 `ORG_DASHBOARD_VIEW`, `AUDIT_LOG_EXPORT`, `SETTINGS_JIRA_MANAGE`, `SETTINGS_SNAPSHOT_MANAGE` 등). 이 덕분에 시스템 관리자 전체 권한을 주지 않고도 해당 작업을 역할 템플릿에 **위임**할 수 있습니다.

### 내장 템플릿 (빈 DB 최초 기동 시)

최초 기동 시, OsWL은 나중에 조정할 수 있는 세 가지 템플릿을 생성합니다:

| 템플릿 | 용도 | 요약 |
|--------|------|------|
| **Admin** | 플랫폼 운영 | 권한 목록 전체 |
| **Developer** | 스캔·분석·조치 담당 | 프로젝트·스캔·보안 센터(상태 업데이트 및 내보내기 포함), 라이선스 조회/내보내기, VCS·CLI 키 |
| **Viewer** | 읽기 전용 이해관계자 | 프로젝트·스캔·보안 센터·라이선스 페이지 조회 및 내보내기 — 스캔 제출·설정 불가 |

이 이름은 **OsWL 인스턴스 전체 기능**을 뜻하며, “프로젝트 #42의 멤버”와 **동일하지 않습니다**.

---

## 레이어 B — 프로젝트 멤버십

- **`project_members`** 테이블에 저장 (사용자 × 프로젝트).
- “**프로젝트 ID X** 데이터에 접근 가능한가?”에 답합니다.
- 보안 센터, 스캔 기록, 라이선스 내보내기, API 키 등 프로젝트 단위 화면·API에서 **`ProjectAccessService`** 로 검사합니다.

### 프로젝트 멤버 역할 (기술)

각 멤버십 행에는 프로젝트 단위 역할이 있습니다:

| 값 | 현재 의미 |
|----|-----------|
| **ADMIN** | 프로젝트 생성 시 생성자에게 부여 |
| **MEMBER** | 그 외 멤버 기본값 |

현재는 **기능 허용 여부는 레이어 A(권한)** 가 결정합니다. 멤버십은 주로 **다른 프로젝트 URL로의 무단 접근(IDOR)** 을 막습니다. 향후 ADMIN/MEMBER 필드를 활용해 "프로젝트 소유자 vs 게스트"를 더 세분화하는 규칙이 추가될 수 있습니다.

### 멤버십이 자동으로 생기는 경우

- **프로젝트를 만든 사용자** → 프로젝트 **ADMIN** 멤버.
- 기동 시, 멤버가 없던 기존 프로젝트에 생성자를 넣는 부트스트랩이 한 번 실행됩니다.

**협업 참고:** 다른 사용자에게 기존 프로젝트 접근을 주려면 `project_members`에 포함되어야 합니다(생성자는 현재 자동으로 등록되며, 그 외 팀 배정은 운영 프로세스나 향후 UI가 필요할 수 있습니다).

## 레이어 C — 시스템 관리자

- 사용자 계정의 **시스템 관리자** 플래그 (설정 마법사에서 생성).
- **설정 → 관리자** (사용자, 역할 템플릿, 감사 로그).
- **프로젝트 멤버십 검사 생략** — 모든 프로젝트 ID 접근 가능.
- 로그인·2FA·세션 보안은 다른 사용자와 동일합니다.
- 많은 관리자 엔드포인트는 시스템 관리자 플래그 **또는** 전용 권한 **둘 중 하나**를 허용합니다. 예:
  - `/api/admin/snapshot/**` (오프라인 스냅샷 상태, 번들 가져오기/내보내기, wanted-list 내보내기) → `SETTINGS_SNAPSHOT_MANAGE`
  - `/api/settings/cache/**` (캐시 TTL 및 수동 캐시 삭제) → `SETTINGS_CACHE_MANAGE`
  - 감사 로그 내보내기 (`/api/admin/audit-logs/export`) → `AUDIT_LOG_EXPORT`
  - 사용자·역할 템플릿 관리와 감사 로그 **조회**는 여전히 **시스템 관리자 전용**입니다.

혼동 주의:

- 역할 템플릿 이름 **“Admin”** → 권한 묶음만  
- 프로젝트 멤버십 **ADMIN** → 해당 프로젝트 생성자 등

## 함께 동작하는 예

| 사용자 | 역할 템플릿 | 프로젝트 #5 멤버? | 프로젝트 #5 보안 센터를 열 수 있나? |
|--------|-------------|-------------------|--------------------------------------|
| 시스템 관리자 | 무관 | 선택 | 가능 (C가 멤버십 검사를 우회) |
| Developer | Developer | 예, #5 프로젝트 멤버 | 가능 (A + B) |
| Developer | Developer | 아니오, #5에 없음 | 불가 — 스캔 권한이 있어도 B에 막힘 |
| Viewer | Viewer | 예, #5 프로젝트 멤버 | 가능, Viewer 템플릿 범위의 읽기 전용 기능만 |
| Viewer | Viewer | 예, 다만 `SCAN_SUBMIT` 없음 | CLI 스캔 제출 불가(A), B만 충족하면 조회는 가능 |

## CLI 스캔 (추가 조건)

`POST /api/scan` 은 자동화용입니다.

1. 유효한 **프로젝트 API 키**  
2. **`SCAN_SUBMIT`** 권한을 가진 제출자의 **이메일 + 비밀번호** (레이어 A)  
3. 해당 프로젝트 **`project_members`** 등록 (레이어 B)  

실패 시 **감사 로그**에 기록됩니다. [CLI 연동](CLI-Integration.md), [스캔 API 보안](Scan-Api-Security.md) 참고.

## 운영·거버넌스

- OsWL은 세션 로그인, 선택적 2FA, 권한 검사, 프로젝트 멤버십, API 키, 속도 제한, 감사 로그, 강화된 프로덕션 기본값 등 **다층 방어(defense in depth)**를 전제로 설계되었습니다.
- 운영 세부 사항(환경 변수, 리버스 프록시, 헬스체크)은 [운영 배포 체크리스트](Production-Deployment-Checklist.md)를 참고하세요.
- 기술적인 적용 지점과 엔드포인트 목록: [프로젝트 접근 제어](Project-Access-Control.md)
