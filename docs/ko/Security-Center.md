# 보안 센터

저장된 조회 결과와 OSV 공통 수정 판정은 중첩 키를 포함한 JSON 중복 키, 뒤따르는 JSON 값, 숫자·불리언의 문자열 필드 변환을 거절합니다. 모호한 조회 결과는 STORAGE/UNAVAILABLE, 모호한 공통 수정 판정은 STORAGE_ERROR로 처리해 공통 수정 버전을 제시하지 않습니다. 읽기만으로 원래 저장 문자열이나 개별 발견의 수정 정보를 바꾸지 않으며, 이후 성공한 새 조회는 현재 캐시를 갱신할 수 있습니다.

온라인 GitHub Advisory 응답도 페이지를 해석하기 전에 중복 JSON 필드와 후속 JSON 값을 거절합니다. 모호한 페이지는 조회 미완료로 처리합니다. 이전 페이지에서 독립적으로 확인한 취약점은 유지하되 전체 조회가 끝나지 않았으므로 수정 후보는 보류합니다. 공급자 응답의 진위를 인증하거나 오프라인 스냅샷 해석을 바꾸는 기능은 아닙니다. 같은 공지가 한 페이지 또는 여러 페이지에서 활성·철회 상태로 충돌하면 조회 미완료로 남기고 수정 후보를 보류합니다. 활성 응답에서 관찰한 취약점은 유지하며, 충돌하는 수명 상태 중 하나를 현재 revision으로 선택하지 않습니다. 일관되게 철회된 항목은 계속 제외합니다. npm·Cargo·Go·PyPI·Maven·NuGet은 온라인 빈 응답이나 완료된 빈 스냅샷을 조회 완료로 인정하기 전에 기존 생태계별 비교기로 설치 버전을 검증합니다. 지원하지 않는 구체 버전 문법은 공지가 없어도 미확인으로 남습니다. 다른 생태계의 버전 순서 지원을 추가하는 변경은 아닙니다. OSV도 npm·Cargo/crates.io·Go·PyPI·Maven·NuGet의 구체 버전 문법을 검사한 뒤 조회 완료 여부를 결정하며, 빈 온라인·스냅샷 결과에도 적용합니다. 해당 지원 문법이 잘못되면 개별·공통 수정 안내를 보류하되 사용 가능한 취약점과 스냅샷 원래 후보는 유지합니다. 원천의 최신 여부와는 별도 검사이며 다른 생태계의 비교기를 추가하지 않습니다. OSV 배치·후속 페이지·공지 상세 응답은 해석 전에 중복 JSON 필드와 후속 JSON 값을 거절합니다. 읽을 수 없는 첫 배치는 미완료로 남고, 상세 실패는 조회한 공지 ID만 유지합니다. 후속 페이지 실패는 앞서 확인한 취약점과 개별 근거를 유지하지만 공통 수정 버전과 조회 완료 판정은 보류합니다.

GitHub Advisory 조회가 완료되면 설치 버전이 포함되지 않은 범위도 포함해 동일 공지의 검증된 모든 범위에서 공급자가 제시한 수정 후보를 검토합니다. 후보는 설치 버전보다 높고 해당 공지의 모든 수집 범위를 벗어나야 합니다. 예를 들어 2.0.0이 다른 구간에 여전히 취약하지만 공급자가 제시한 3.0.0이 모든 구간을 벗어나면 3.0.0을 후보로 유지합니다. 비영향 구간을 설치 버전의 취약점으로 추가하거나 패키지 전체의 안전한 목표 버전을 확정하는 것은 아닙니다. [GitHub 필드 정의](https://docs.github.com/en/graphql/reference/security-advisories#securityvulnerability)를 참고하세요.

DB 통합 검사는 온라인 클라이언트에 합성 중첩 범위를 제공하고 선택된 결과를 명시적인 테스트 ZIP으로 만들어 H2 및 별도 PostgreSQL DB에 반입한 뒤 오프라인 클라이언트로 조회합니다. 최신 기준일에서는 동일 공지·심각도·수정 버전 3.0.0이 유지됩니다. 8일 경과 또는 기준일 누락은 취약점과 저장 후보를 보존하지만 오프라인 수정 안내를 보류하며, 없는 버전 키는 조회 완료가 아닙니다. 기준일은 모의 조건입니다. 이는 importer/client 경로 검증이며 CLI 수집·실제 GitHub 접속 검증은 아닙니다.

패치 필터는 컴포넌트/라이브러리 ID를 한 번 정렬한 뒤 필요한 근거 필드만 배치 조회하고 선택된 컴포넌트 엔티티만 로드합니다. 화면과 필터는 조회 시각·패치 판정 규칙을 공유하며, 미확인 조회·CPE 후보·심각도 누락·공백뿐인 수정 버전을 동일하게 처리합니다. 컴포넌트마다 발견 항목 1개를 둔 50,000개 로컬 H2 단일 측정에서 엔티티 로드는 약 10만 개에서 1~305개로 줄었고, 정확한 일치 결과 25,000건의 페이지를 1.1~1.8초에 반환했습니다. 메모리 DB를 포함한 전체 JVM의 측정 힙은 512MiB 한도에서 약 460MiB였습니다. 개별 관측값이며 운영 지연 백분위나 메모리 보장은 아닙니다. 동시 요청, 라이브러리당 발견 항목이 많은 데이터, 운영 PostgreSQL 규모는 추가 검증이 필요합니다.

추가 로컬 H2 검사에서는 컴포넌트 5,000개에 발견 항목을 각각 10개씩 두고, 0·1·24·25페이지를 읽는 서비스 호출 4개를 동시에 실행했습니다. 각 호출의 일치 결과는 2,500건이었고 비어 있지 않은 세 페이지의 300개 컴포넌트에는 중복이 없었습니다. CPE 후보 1개와 패키지 근거 9개가 섞인 라이브러리도 패치 가능 결과에서 제외됐습니다. 단일 실행에서 호출은 5.0~5.3초, 전체 엔티티 로드는 3,608개, 전체 JVM 측정 힙은 약 379MiB였습니다. HTTP 동시 요청, 운영 PostgreSQL 성능, 동시 갱신을 보장하는 검사는 아닙니다.

심각도 필터는 화면 집계와 동일하게 CPE 후보를 제외하며, 미평가 필터는 심각도 누락과 NONE을 모두 포함합니다. 심각도 필터를 선택하지 않으면 후보도 계속 표시됩니다. 패치 필터는 컴포넌트 행과 같은 판정을 사용합니다. 조회 미완료나 CPE 후보가 있으면 패치 가능/불가능에 포함하지 않으며, 심각도 누락만으로 개별 수정 정보를 버리지 않습니다. 버전 상태 필터는 발견 항목이 없는 컴포넌트에만 적용합니다. 패치 가능 표시는 개별 수정 정보가 있다는 뜻이며 공통 안전 업그레이드 대상을 입증하지 않습니다. 패치 필터를 선택하면 다른 필터를 만족하는 행을 100개씩 평가한 뒤 요청 페이지와 정확한 전체 건수를 계산합니다. 해당 행 전체를 확인하므로 대규모 스캔에서는 조회 비용이 늘 수 있습니다. 위험순 정렬은 후보를 제외한 심각·높음·중간·낮음·미평가 건수를 차례로 내림차순 비교한 뒤 CPE 후보 수를 비교합니다. 동률은 이름과 컴포넌트 ID로 정합니다. 낮은 심각도 건수가 많아도 더 높은 심각도 건수를 앞설 수 없습니다. 후보는 계속 표시되지만 원래 심각도가 심각도 집계 순위를 높이지 않습니다. 정렬 값이 0이라는 사실은 조회 완료나 안전을 입증하지 않습니다.

컴포넌트 표·상세 헤더·인쇄 표·CSV의 심각도 집계에서도 CPE 후보를 제외하고 별도 후보 수를 표시합니다. 후보만 있는 컴포넌트는 패치 가능 여부를 미확인으로 유지하며 취약점 없음 배지를 표시하지 않습니다. 심각도 누락과 NONE은 미평가로 합산합니다. CSV는 기존 열 뒤에 `CPE Match Review Candidates` 열을 추가하므로 열 개수를 고정한 연동은 이를 반영해야 합니다. 이 컴포넌트 화면은 여전히 공유 라이브러리 캐시를 조회하므로 보존된 과거 요약과 다를 수 있습니다.

스캔 요약의 심각도 집계와 조직 KEV 집계는 매칭 검토가 필요한 CPE 후보를 제외합니다. 보안 센터·프로젝트 카드·조직 화면·위험 추세에는 후보 수를 별도로 표시합니다. 같은 발견에 패키지 근거가 있으면 기존 분류를 유지합니다. V45는 새 보관 기록에 후보 수를 저장합니다. 보존 판정이나 후보 수가 없는 이전 보관 기록은 원래 집계를 유지하고 구분 미상 안내를 표시하며, 임의로 재분류하거나 0으로 바꾸지 않습니다. 상세 행의 분류와 현재 공유 캐시·과거 데이터의 차이는 이 요약 집계와 별개의 범위입니다.

취약점 조회가 미완료이면 패치 가능성은 알 수 없음으로 유지하며 개별 취약점과 저장된 수정 버전은 그대로 표시합니다. 조회가 완료됐을 때 패치 가능은 활성 발견 중 수정 버전이 기록된 항목이 있다는 뜻이며, 하나의 버전으로 모든 취약점이 해결된다는 의미는 아닙니다. 패치 불가는 활성 발견에 기록된 수정 버전이 없다는 뜻으로, 공급자에 수정 버전이 전혀 없음을 증명하지 않습니다. 공통 업그레이드 추천은 별도로 검증합니다.

스캔 근거 안내에는 선택한 스캔 ID, 기록 시각과 등록된 저장소가 표시됩니다. 당시 판정이 보존되지 않은 이전 자료만으로는 샘플·수동 제출·실제 저장소 스캔 여부를 확인할 수 없습니다. 0건을 정상 스캔의 증거로 보지 말고 실제 저장소 Quick Import 또는 새 CLI 스캔으로 확인하세요. 컴포넌트 상세는 현재 공유 조회 캐시를 보여주므로 스캔 당시 결과와 다를 수 있습니다. 보존 판정이 있어도 모든 출처의 조회 성공을 보장하지 않습니다.

보안 센터는 OsWL의 기본 취약점 관리 인터페이스입니다. 프로젝트의 최신 스캔에서 감지된 컴포넌트에 영향을 미치는 모든 CVE를 필터링·정렬 가능한 목록으로 제공합니다.

URL: `/projects/{id}/security-center`

**접근:** `SECURITY_CENTER_VIEW`(또는 시스템 관리자) 및 [프로젝트 멤버십](Authorization-Layers.md) 필요. 내보내기·인쇄는 `SECURITY_CENTER_EXPORT`, 상태 변경은 `SECURITY_CENTER_UPDATE_STATUS`.

## CVE 목록 이해하기

보안 센터의 각 행은 스캔된 컴포넌트와 연결된 하나의 **CVE**(Common Vulnerabilities and Exposures) 항목을 나타냅니다.

| 컬럼 | 설명 |
|---|---|
| **컴포넌트** | 라이브러리 이름과 버전 |
| **에코시스템** | 패키지 에코시스템 (MAVEN, NPM, PYPI, …) |
| **CVE ID** | deps.dev/OSV의 CVE 또는 GHSA 식별자 (예: `CVE-2021-44228`) |
| **CVSS 점수** | 수치 심각도 점수 (0.0–10.0) |
| **심각도** | CRITICAL / HIGH / MEDIUM / LOW |
| **수정 버전** | 권장 수정 버전 (알려진 경우) |
| **상태** | 현재 분류 상태 |
| **패치 가능성** | 수정 사항 존재 여부 |

## 심각도 수준

OsWL은 표준 CVSS 3.x 구간에 따라 기본 점수를 심각도로 분류합니다:

| 심각도 | CVSS 점수 범위 | 의미 |
|---|---|---|
| **CRITICAL** | 9.0 – 10.0 | 원격 악용 가능, 높은 영향도 — 즉시 수정 필요 |
| **HIGH** | 7.0 – 8.9 | 심각한 위험 — 이번 스프린트 내 우선 처리 |
| **MEDIUM** | 4.0 – 6.9 | 보통 위험 — 가까운 시일 내 수정 |
| **LOW** | 0.1 – 3.9 | 최소 위험 — 편의에 따라 수정 |
| **NONE** | 0.0 | 정보 제공용 / 활성 점수 없음 |

## CVE 상태 라이프사이클

프로젝트의 모든 CVE에 다음 상태 중 하나를 지정할 수 있습니다:

| 상태 | 의미 |
|---|---|
| **OPEN** | 새로 감지됨 — 검토 필요 |
| **IN_PROGRESS** | 적극적으로 수정 중 |
| **SUPPRESSED** | 인지된 위험; 현재 맥락에서 즉각적 우선순위 아님 |
| **FALSE_POSITIVE** | 적용 불가로 확인됨 (예: 취약한 코드 경로가 도달 불가) |
| **RESOLVED** | 수정 완료 — 업그레이드 적용 또는 컴포넌트 제거됨 |

> 상태 업데이트에 필요한 권한: `SECURITY_CENTER_UPDATE_STATUS` 또는 시스템 관리자.

## 필터링 및 정렬

보안 센터 상단의 필터 바를 사용하여 목록을 좁힐 수 있습니다:

* **심각도** — CRITICAL / HIGH / MEDIUM / LOW
* **상태** — OPEN / IN_PROGRESS / SUPPRESSED / FALSE_POSITIVE / RESOLVED
* **에코시스템** — MAVEN / NPM / PYPI / 기타
* **패치 가능성** — Patchable / Non-Patchable / Unknown
* **검색** — CVE ID 및 컴포넌트 이름 전체 텍스트 검색

컬럼 헤더를 클릭하면 오름차순/내림차순으로 정렬됩니다. 별도의 **정렬** 셀렉터로 기본 정렬 기준을 고를 수 있습니다: **위험도 (기본값)**(높은 심각도 우선), **이름**, **라이선스 위험도**.

## 일괄 상태 업데이트

1. 체크박스를 사용하여 하나 이상의 CVE를 선택합니다.
2. 작업 도구 모음에서 **상태 업데이트**를 클릭합니다.
3. 드롭다운에서 새 상태를 선택합니다.
4. 확인합니다.

선택된 모든 CVE가 단일 트랜잭션으로 업데이트됩니다.

| SARIF | `GET /api/projects/{projectId}/sarif` | SARIF 2.1.0, GitHub 코드 스캐닝 업로드 가능 |
| 컴플라이언스 리포트 | `GET /projects/{projectId}/security-center/compliance-report` | 인쇄용 HTML (*인쇄 → PDF로 저장* 사용) |
| CVE / 라이선스 CSV | — | 선택한 완료 스캔의 컴포넌트 요약 (기본값: 최신 완료 스캔) |

컴포넌트 CSV는 기존 열 뒤에 `Vulnerability Lookup Complete`, `Lookup Outcomes`, `Lookup Attempt At`을 추가합니다. `No`이면 CVE 0건만으로 조회 완료를 판단할 수 없습니다. `Yes`는 컴포넌트 화면과 같은 완료 기준이며 안전성을 보장하지 않습니다. 출처별 결과는 이름순 `SOURCE=STATUS` 쌍으로 표시하고, 없는 과거 metadata는 빈 값으로 유지합니다. 출처별 결과가 없는 레거시 캐시는 수집 시각이 있어도 `No`입니다. 영구 캐시 설정에서도 다음 분석 시 재조회합니다. 조회 시각은 저장된 로컬 시각이며 취약점 데이터의 발행일이나 최신성 보장이 아닙니다. 열 개수를 고정한 소비자는 추가된 세 열을 반영해야 합니다.

일괄 작업에는 선택한 컴포넌트를 모두 수정 버전으로 올리는 **업그레이드 PR 생성**도 포함됩니다.

자세한 내용은 [v1.0.4 새로운 기능](Whats-New-v1.0.4.md)을 참고하세요.

## 컴포넌트 상세

컴포넌트 이름을 클릭하면 **컴포넌트 상세** 사이드 패널이 열립니다:

취약점이 있고 현재 버전과 다른 문서화된 수정 대상을 선택할 수 없다면 자동 PR 생성은 최신 버전으로 대체하지 않습니다. 최신 버전이라는 사실만으로 보안 수정이 입증되지는 않습니다. 최신 버전으로의 일반 업데이트 PR은 CVE가 없고 오래된 버전임이 확인된 경우에만 허용하며, 버전 상태 미확인만으로는 허용하지 않습니다.

단일·일괄 PR의 VCS 변경 직전에 OSV로 설치 버전과 제안 버전을 다시 조회합니다. 보안 대상은 현재 OSV 원문에서 계산한 공통 수정 버전과 일치하고, 저장된 취약점의 근거가 확인되며 수정 충돌이 없어야 합니다. 대상 버전의 OSV 결과는 비어 있어야 하고, deps.dev 버전 조회도 완료되며 advisory ID가 없어야 합니다. GitHub Advisory가 설정되었거나 이전에 필요했던 경우 해당 출처도 완전한 빈 결과가 필요합니다. 오프라인에서는 대상 버전의 스냅샷 항목이 필요하며 누락·노후화 시 PR을 보류합니다. CPE·저장소 식별과 버전 근거가 지원되지 않는 생태계는 미검증으로 남습니다. 이 검사는 해당 패키지 버전과 조회한 출처 범위이며 업그레이드로 바뀌는 의존성 그래프 전체를 검증하지 않습니다. 화면과 PR 후보 선택은 심각도가 높은 개별 수정 버전 대신 현재 유효한 OSV 공통 판정을 사용합니다. 근거 누락·만료·조회 미완료·일부 취약점 근거 미확인·충돌 시 공통 후보는 미확인으로 남기며 개별 공지의 수정 정보는 유지합니다. 공통 후보도 생성 직전 대상 검사에서 거부될 수 있습니다.

* deps.dev 프로젝트 레코드를 기반으로 한 라이브러리 설명, 홈페이지/소스 저장소 링크
* 해당 라이브러리의 모든 CVE (전체 CVSS 분석 포함) — 위쪽 배지와 구분된 **보안 취약점** 영역에 그룹화
* 라이선스 이름 및 컴플라이언스 상태
* AI 생성 라이선스 리스크 요약
* 최신 버전 및 지원 중단 공지
* 전체 의존성 경로 (직접 vs. 전이적)
* **OpenSSF Scorecard** 점수, 공급망 휴리스틱이 표시한 **악성 패키지** / **typosquat 위험** 배지 (v1.0.4)
* Jira 연동이 구성된 경우 **Jira 이슈 생성** 버튼 (v1.0.4). 생성 후에는 배지가 바로 해당 Jira 이슈로 연결되며, 생성에 실패하면 앱 전반에서 쓰이는 것과 동일한 스타일의 토스트로 실패 사유가 표시됩니다

접힌 상태에서는 긴 CVE 설명이 축약되지만, 행을 클릭해 펼치면 어드바이저리 전문이 표시됩니다. 왜 취약점인지 항상 확인할 수 있습니다.

패널에서 **패치 적용 (PR 생성)**과 **조치 연기**도 실행할 수 있습니다. 조치 연기는 사유와 만료 기간(1주 / 1·3·6개월 / 직접 지정 / 무기한)을 기록합니다. 직접 지정 날짜는 **미래 날짜**여야 합니다 — 과거이거나 형식이 잘못되면 HTTP 400으로 거부되며, 날짜 선택기도 내일부터만 고를 수 있습니다.

PR/MR 생성이 완료되면 성공 패널에 눈에 잘 띄는 **PR/MR 보기** 버튼과 접었다 펼 수 있는 **"어떤 코드가 바뀌었나요?"** 요약이 표시됩니다 — 패치된 매니페스트 파일 경로와 버전 변경 내용(예: `pom.xml`: `log4j-core 2.14.1 → 2.17.0`)을 보여줍니다.

컴포넌트의 연기 기간이 만료되면(야간 스케줄러) 연기가 해제되고, 최근 7일 내 연기가 끝난 컴포넌트가 있으면 Security Center 상단에 닫을 수 있는 **🦉 올빼미 리마인드 배너**가 나타나 재검토를 안내합니다.

## AI 보안 인사이트

AI 제공업체가 설정된 경우(**설정 → AI**), 스캔 보강 과정에서 자유서술 AI 인사이트를 생성합니다. v1.0.4부터 스캔 단위 인사이트는 모두 스캔당 1회의 통합 AI 호출로 생성됩니다:

* **보안 현황 인사이트** — 현재 CVE 수 및 심각도 분포에 대한 전반적 평가로, 보안 센터 상단에 한 단락짜리 **AI 인사이트** 요약으로 표시
* **보안 리스크 트렌드 인사이트** — 이전 스캔과 비교한 개선·악화 여부로, [리스크 트렌드](Risk-Trend.md) 페이지에 표시

인사이트는 스캔당 한 번 생성됩니다. AI 제공업체를 처음 활성화하면 누락된 인사이트가 자동으로 채워지고, AI 프롬프트 언어를 변경하면 최근 스캔의 인사이트가 재생성되며, 라이선스 페이지에서 수동으로 다시 생성할 수도 있습니다.

## 패치 가능성

OsWL은 라이브러리의 모든 CVE에서 `fixVersion` 필드를 기반으로 패치 가능성을 도출합니다:

| 상태 | 조건 |
|---|---|
| **PATCHABLE** | 알려진 수정 버전이 있는 CVE가 하나 이상 존재 |
| **NON_PATCHABLE** | CVE는 존재하지만 알려진 수정 사항 없음 |
| **UNKNOWN** | CVE 없음 또는 CVE 데이터 미보강 |

## 데이터 출처

CVE 데이터는 두 출처에서 가져와 병합됩니다:

* **deps.dev** — `GetAdvisory`로 GHSA 어드바이저리, CVE 별칭, CVSS 점수, 제목 조회
* **OSV** (Open Source Vulnerabilities) — `POST https://api.osv.dev/v1/querybatch`로 요약, 수정 버전, **CWE ID**(`database_specific.cwe_ids`) 조회

CWE 식별자(예: `CWE-79`)는 OSV가 제공할 때 컴포넌트 상세 패널에 표시됩니다.

v1.0.4부터 우선순위 판단용 피드 두 개가 함께 병합됩니다.

* **CISA KEV** — *Known Exploited Vulnerabilities* 목록. KEV 등재는 실제 공격 사용이 확인되었다는 뜻이므로 트리아지 순서에서 CVSS 점수보다 우선합니다.
* **EPSS** (FIRST.org) — 향후 30일 내 악용 확률로, KEV에 없는 항목의 순위를 정하는 데 사용됩니다.

test/dev 전용 의존성은 scope가 태그로 붙고 목록에서 숨길 수 있어 운영 리스크가 드러납니다. 제거가 아니라 태그이므로 SBOM에서는 아무것도 사라지지 않습니다.

보강은 각 스캔 후 자동으로 실행되며, **설정 → 캐시**(`/api/settings/cache`) 정책에 따라 갱신됩니다.

## 내장 소스 분석의 완전성

시크릿·IaC의 파일 읽기 또는 디렉터리 순회 실패는 이미 수집한 탐지 결과와 함께 미완료 표시를 유지합니다. 시크릿 규칙이 없을 때도 미완료 표시를 남깁니다. 기존 미완료 표시 유형은 시크릿 탐지 차단 옵션이 꺼져 있어도 게이트의 완료 판정을 막습니다. 읽을 수 있는 빈 디렉터리는 여전히 0건을 반환합니다. 모든 제외 파일·분석 예산·비활성 스캐너·다른 반입 경로의 소스 누락을 처리한 것은 아닙니다. 내장 스캐너의 탐지 제한 300건에 도달하면 보존된 탐지와 별도로 미완료 표시 1건을 남깁니다. 정확히 300건이어도 해당 지점에서 중단되어 모든 입력의 끝까지 검사했음을 확인할 수 없으므로 미완료로 처리합니다. 이미 수집한 탐지 결과는 삭제하지 않습니다.

분석 대상 파일이 1,000,000바이트를 넘으면 조용히 0건을 반환하는 대신 미완료로 기록합니다. 제한 이하 파일은 계속 분석합니다. 기존 바이너리 확장자 제외와 IaC 대상 분류를 먼저 적용한 뒤 크기를 확인합니다. 파일별 제한에 대한 처리이며 전체 바이트·시간 예산은 별도 잔여 작업입니다.

시크릿 분석은 손상되거나 잘린 UTF-8 입력을 미완료로 처리합니다. 잘못된 바이트를 대체 문자로 바꾸어 읽기 성공으로 처리하지 않습니다. 다른 정상 파일의 탐지 결과는 유지합니다. 대체 문자가 실제로 인코딩된 경우를 포함해 정상 UTF-8은 계속 읽습니다. 다른 문자 인코딩을 자동으로 추측하거나 변환하지 않습니다.

확장자 제외를 통과한 파일에서 NUL 문자를 만나 시크릿 분석이 중단되면 미완료로 기록합니다. 중단 전에 수집한 탐지는 보존하며 읽지 않은 나머지 부분을 검사 완료로 취급하지 않습니다. 기존 바이너리 확장자 제외 정책은 유지합니다.

## Python 패키지 조회 식별자

OSV 응답에 발견 항목이 없어도 기존 Python 패키지 이름 검증을 적용합니다. 잘못된 이름은 온라인·오프라인 모두 조회 미완료로 남깁니다. 저장된 발견 항목은 불완전한 근거로 유지하지만 수정 버전 안내는 보류하며 저장 원본의 후보는 변경하지 않습니다. 정상적인 구분자 조합과 한 글자 이름은 계속 허용합니다. 규칙은 [PyPA 이름 명세](https://packaging.python.org/en/latest/specifications/name-normalization/)를 따르며, 잘못된 이름에서 의도한 패키지를 추측해 보정하지 않습니다.

OSV bulk 수집도 조회와 같은 식별자 검증을 사용해 npm/Cargo·Go·Python·Maven·NuGet 버전과 기존 패키지 이름 규칙을 확인합니다. 공지에 등장하지 않은 잘못된 요청도 미확인으로 기록하고 정상 요청의 수집은 계속합니다. 미확인 키를 만들 수 없을 정도로 식별자가 누락되면 수집을 실패시킵니다. 다른 생태계의 버전 비교기를 추가한 것은 아닙니다. CLI 출력은 해당 요청을 unresolved.jsonl에 보존합니다.

번들을 생성할 때 OSV가 명시적으로 미확인으로 남긴 결과는 다른 OSV 공지의 발견 항목이나 deps.dev 패키지 정보가 있어도 미확인 상태를 유지합니다. 확인된 발견 항목은 삭제하지 않고 unresolved.jsonl과 함께 보존합니다. 수집 과정의 불확실성을 유지하는 변경이며 모든 공급원의 개별 완전성 모델을 완성한 것은 아닙니다.

로컬 CLI → H2 반입 → 오프라인 OSV 조회 검증에서 전체 번들 이후 차분 갱신으로 명시적 미확인과 수집 완료 사이를 양방향 전환했습니다. 확인된 발견 항목과 개별 수정 후보를 유지하면서 미확인 표시가 추가·제거됨을 확인했습니다. 현재 bulk CLI 레코드는 공지 범위 원문을 생략하므로 조회 완료여도 공통 수정 버전은 NO_RANGE_EVIDENCE로 보류하며, 미확인 조회는 INCOMPLETE_LOOKUP으로 보류합니다. 이 한계는 온라인·오프라인 수정 버전의 완전한 동등성이 검증됐다는 뜻이 아닙니다.

배포판 bulk 다운로드는 [OSV 생태계 이름 안내](https://google.github.io/osv.dev/data/#ecosystem-naming)에 따라 Debian·Alpine·Ubuntu 상위 버킷을 사용합니다. 공지 매칭에는 배포판 버전 식별자를 유지해 다른 버전과 섞지 않습니다. 2026-09-13에 세 all.zip 객체의 HEAD 응답 HTTP 200과 Last-Modified 2026-09-12를 확인했습니다. 응답 헤더만 확인했으며 전체 데이터의 완전성이나 재배포 권한이 검증된 것은 아닙니다. 기존 버전별 오프라인 소스 캐시는 현재 상위 버킷 파일명으로 준비해야 합니다.

버전별 Alpine 조회와 bulk 수집도 빈 결과를 완료로 받아들이기 전에 기존 APK 버전 파서를 적용합니다. *·latest 같은 미지원 입력은 미확인으로 유지하고 지원되는 revision·사전 배포 형식은 계속 허용합니다. 캐시의 발견 ID는 보존하지만 잘못된 입력에는 수정 버전을 안내하지 않습니다. 기존 파서의 지원 범위를 사용하는 변경이며 Debian·RPM 버전 비교를 추가하지 않습니다.

APK 숫자 구간의 원래 표기를 보존해 첫 구간 이후 선행 0이 있는 경우의 순서를 반영합니다. [apk-tools 버전 구현](https://raw.githubusercontent.com/alpinelinux/apk-tools/master/src/version.c)과 [문자열 정렬 구현](https://raw.githubusercontent.com/alpinelinux/apk-tools/master/src/blob.c)에서 확인한 동작을 기준으로 합니다. 비교기는 Alpine:과 내부 ALPINE: 표기를 모두 인식하며 패키지·배포판 버전 매칭은 별도로 유지합니다. 합성 테스트로 비교·취약 범위·bulk 수정 후보 선택을 검증했습니다. GPL-2.0-only 상위 소스는 동작 확인에만 사용하고 복제·번들에 포함하지 않았으며 native apk 실행이나 전체 문법 동등성을 검증한 것은 아닙니다.

APK 비교는 숫자 구간·suffix 번호·revision의 생략과 명시적인 0도 구분합니다. 예를 들어 1은 1.0보다, 1.0은 1.0-r0보다 앞섭니다. 명시된 revision 번호 0과 00은 수치상 같은 값으로 유지합니다. 위에 연결한 상위 구현의 토큰 순서를 기준으로 직접 비교와 공지 범위·수정 후보 선택을 검증했습니다. native APK와의 전체 동등성은 아직 미검증입니다.

APK 파서는 v/V 접두사나 앞뒤 공백을 제거하지 않으며 suffix에는 underscore가 필요합니다. 1.0p1·1.0rc1을 1.0_p1·1.0_rc1로 조용히 바꾸지 않습니다. 한 글자 접미사는 정상 문법으로 유지하되 suffix와 구분합니다. 공급자 자료의 미지원 표기는 같은 패키지 버전의 별칭으로 확정하지 않고 불확실하게 남깁니다. 위 상위 문법을 기준으로 하며 전체 문법 지원은 아직 미완료입니다.

APK 파서는 1.0a_p1-r2처럼 문자 접미사 뒤에 underscore suffix와 선택적 revision이 오는 조합을 허용합니다. 문자를 먼저 비교하고 사전 배포·패치 suffix의 순서를 유지합니다. 비교기·OSV 범위/수정 후보·bulk 변환·온라인/오프라인 식별자 검증을 합성 테스트로 확인했습니다. APK의 16진수 hash 부분을 지원하며 native 동등성은 미검증입니다.

여러 APK suffix를 순서대로 보존하며 suffix 번호 생략과 revision·버전 끝으로의 전환을 구분합니다. 사전 배포 suffix는 해당 버전 끝보다 앞서고 패치 suffix는 뒤에 옵니다. 직접 순서·공지 영향 범위·bulk 수정 후보와 다중 suffix의 온라인/오프라인 조회를 검증했습니다. native 동등성은 미검증입니다.

APK ~hash 부분은 대소문자와 접두 길이를 포함한 16진수 문자열로 보존·비교하고 선택적 revision보다 먼저 비교합니다. 비어 있거나 16진수가 아닌 값, 중복되거나 위치가 잘못된 hash는 거절합니다. 이 순서는 APK 생태계 범위에만 적용하며 OSV GIT 범위는 선후 관계 근거가 없으면 계속 미확인으로 남깁니다.
